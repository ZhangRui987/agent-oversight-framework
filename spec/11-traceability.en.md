Rule: every mechanism must correspond to a real lesson; if none is found, suspect it exists for control's sake. The table below grades each mechanism by evidence strength, with incident-corroborated mechanisms placed at the front.

**The traceability relations themselves must be verifiable (added this round).** Ayush Aggarwal and Mohammad Arif Baig, *Enhancing DevSecOps Practices for Secure AI Platforms Using SABSA* (IEEE Internet of Things Journal, **Early Access**, published 2026-07-29, DOI 10.1109/JIOT.2026.3717946) operationalize the SABSA security-architecture framework together with a DevSecOps engineering pipeline, bridging the gap between "abstract risk governance" and "technical implementation", and use IaC (Checkov) scanning to establish **traceability across the multi-layer architecture**. This table (the mechanism traceability table) is currently hand-written and hand-maintained — the sync of its "mechanism → basis" rows against the actual content of the body is not automatically checked; the gate automatically checks citation-key consistency between REFERENCES and spec/, but this table is outside that check. The gap is registered as **open problem #28**. ⚠️ Four limitations (Early Access, no final pagination; the experiment uses a DistilGPT-2 miniature model with **simulated** adversarial vectors — a substantial domain-transfer gap; only **direct** prompt injection is covered, not indirect; the abstract claims only a "robust absolute mitigation rate" without giving a figure) make this a **concept adoption** only: this framework adopts the concept that "traceability can be pipeline-produced", and cites neither the 41.6 ms overhead bound nor any mitigation-rate figure.

## Structure migration declaration: from flat "mechanism → basis" to a CAE three-layer framework (new in v2.22.0)

This table is currently a flat "mechanism → lesson/source → grade → basis" structure. The safety-case methodology provides a more auditable alternative — the **CAE three-layer structure** (Claim–Argument–Evidence). Three path-independent independent sources jointly support this upgrade:

- [key: safety-cases-justification] (arXiv:2403.10462, Clymer / Gabrieli / Krueger / Larsen, 2024-03): proposes the "safety case" — a structured rationale composed of "claim–argument–evidence" three layers, arguing that a system is unlikely to cause a catastrophe in a given operational context. Provides four argument categories (total inability / sufficient control / trustworthiness despite capability / deference to credible AI advisors).
- [key: safety-cases-frontier-ai] (Governance.ai, Buhl / Sett / Koessler / Schuett / Anderljung, 2024-10-28): applies the safety-case methodology to frontier AI governance, arguing its applicability in both industry self-regulation and government regulation, and discussing the practical steps to produce a frontier AI safety case.
- [key: assurance-framework-aies] (arXiv:2504.16937, Kapusta et al., 7 authors, MITRE / DOD CDAO / JHU APL, 2025-04, published at SPIE D+C 2025): proposes a claims-based framework for AI system assurance covering the full lifecycle — complementary to safety cases: safety cases focus on "will it cause a catastrophe", the assurance framework covers "does it continue to meet mission goals from development to retirement".

**The upgrade proceeds in two steps** (as the mapping table recommended): **Step one** (v2.22.0) restructured this section into the CAE three-layer framework — declaring the structure, registering the methodology sources, and annotating the table header with "migration target column"; **no** argument chains were filled in for the 49 rows. **Step two** (v2.23.0, this version) has filled in argument chains row by row — splitting each row's "lesson/source" into "**Claim**: what problem this mechanism solves → **Argument**: why this source supports the claim → **Evidence**: the verifiable citation key of the source", and extended the gate script (item 36 added) to statically check that each row must contain all three CAE markers. ⚠️ Three retention limitations: ① upgrading to CAE does **not replace** formal safety-case certification — it is only an auditable structure for mechanism-level traceability; ② formalizing the CAE structure is not equivalent to the correctness of the arguments themselves — a wrongly composed argument can still be formalized in CAE but is invalid in content, requiring independent review; ③ the workload of filling argument chains is proportional to the row count (49 rows).
