## 接入前置披露：harness 披露卡
本体系多处要求「部署方自评」「采集点说明」「规则可 diff」，但一直缺少统一的输入格式——条款只能靠问，无法靠查。补一道前置要求：任何系统接入本框架前，须提交一份 harness 披露卡，把「模型之外的那一层究竟是什么」讲清楚。
可直接采用现成工件：Harness Engineering for Language Agents (CAR)（Preprints.org，DOI 10.20944/preprints202603.1756.v1）提出的 **HarnessCard**，共 11 个字段（9 项必需、2 项推荐），已逐字核对于该文附录 Table A5：

| # | 字段 | 应披露什么 | 要求 |
| --- | --- | --- | --- |
| 1 | Base model(s) | 模型名称、版本、解码设置，以及任何微调或适配器 | 必需 |
| 2 | Control artifacts | 系统指令、AGENTS.md 类文件、仓库地图、架构规则、模式定义、测试、linter、完成判据 | 必需 |
| 3 | Runtime policy | 记忆类型、压缩或摘要策略、检查点、重试与回滚策略、预算限制 | 必需 |
| 4 | Action substrate | 工具、API、浏览器或 GUI 访问、代码执行、接口模式、MCP 使用 | 必需 |
| 5 | Execution topology | 单 Agent 还是多 Agent 结构、规划者 / 验证者角色、复核回路、路由逻辑 | 必需 |
| 6 | Feedback stack | 测试、评分器、反思提示、隐藏检查、人工干预、修复回路 | 必需 |
| 7 | Governance layer | 权限、沙箱、升级规则、策略检查、来源日志、审计支持 | 必需 |
| 8 | Observability | 存储的轨迹、重放支持、延迟与成本日志、失效分类 | 必需 |
| 9 | Evaluation protocol | 任务集、运行次数、成功判据、方差处理、留出检查或预算限制 | 必需 |
| 10 | Release artifacts | 提示词或程序、工具规格、轨迹、配置、环境搭建、可复现说明 | 推荐 |
| 11 | Known limitations and risks | 未解决的失效模式、可移植性保留意见、安全顾虑、红队发现 | 推荐 |

为什么必须有它：本体系的多个机制都以「harness 是什么」为输入——G×S 二维定级需要执行拓扑与动作基底（字段 4、5）；**其第三根轴 H（harness 可观测性成熟度）逐级依赖字段 4 + 6（H1 的工具与测试注册表）、字段 2 + 11（H2 的 Agent 指南、架构说明与已知缺陷清单）、字段 6 + 8 + 9（H3 的确定性检查、重放支持、失效分类与验证协议）；G 轴的可逆性判据依赖字段 3 的回滚策略与字段 4 的外部接口面**；E 子系统的采集点选择需要可观测性说明（字段 8）；「谁有权修改规则」一节需要控制工件与运行时策略的清单（字段 2、3）。缺了这份披露，前述条款只能依赖问询与信任，无法依赖核查。
⚠️ **定位限定**：来源为 C 级（立场论文，作者自陈无受控消融）。因此本卡定位为**披露要求，不是技术门槛**——它不设合格线，只要求说清楚；是否合格由定级流程判定，不由本卡判定。**不得**依据某系统未提交披露卡而直接推定其不安全。
**监管侧的独立依据（本卡必要性的第三条理由）。** 上述理由全部来自本体系内部——披露卡是本体系多个机制的输入。还有一条来自外部的独立理由：一份针对 AI agent 提供者的系统性监管映射工作文件（*AI Agents Under EU Law*，arXiv:2604.04604，9 位作者，2026-04-06）在给出九类 agent 部署分类学与十二步合规架构之后得出结论：**提供者的基础性合规任务，是对该 agent 的外部动作、数据流、所连接的系统与受影响的人做穷尽清点。** 这与本卡的内容高度重合：外部动作与所连接的系统对应字段 4（动作基底：工具、API、浏览器或 GUI 访问、代码执行、接口模式、MCP 使用）与字段 5（执行拓扑）；数据流对应字段 3（运行时策略：记忆类型、压缩或摘要策略、检查点）与字段 4 的接口模式部分。
⚠️ 该依据的三项限定：其一，该文自陈为 **Working Paper，并随 M/613、M/606 与 Digital Omnibus 等草案更新**，内容可能变动；其二，它是**作者的监管映射分析，不代表监管方立场**——引用时必须表述为「一份第三方系统性映射工作文件论证……」，**不得**表述为「欧盟 AI Act 要求……」；其三，因此它只能作为本卡必要性的**旁证**，不构成合规义务，也不改变本卡「披露要求而非技术门槛」的定位。
**本卡的一处空缺（登记为 #26）。** 该文列举的第四类对象——**受影响的人**——在本卡 11 个字段中没有专门承载者：字段 11「已知局限与风险」讲的是系统自身的失效模式与安全顾虑，字段 7「治理层」讲的是权限与审计支持，两者都不回答「这个 agent 的动作会作用到谁身上」。这不必然意味着需要增设字段——受影响方可能已在定级流程的「外部性」判据中被覆盖——但这是一个尚未判定的问题，故登记为未解问题 #26。**在判定之前，本条不得作为推定任何系统不合规的依据。**
## 一句话收敛
收敛：治理的重心仍在 L1，但证据的重心必须下移到内核——因为当 700 个 Agent 能自己长出指挥体系、并能伪造沙箱的工具调用记录时，「谁在记录」比「记录了什么」重要得多。
衡量这套体系成败的指标，不是「抓到多少次违规」，而是「人类的可委托边界扩展了多少」——有多少此前不敢交给 AI 的任务，现在敢了。
A8（规划—执行分离，候选架构）：将「二号主导任务拆解、一号沦为纯执行工具」作为候选架构。该架构在理论上更彻底——执行走样的空间被压缩到零，因为一号不持有对任务的解读权，「对策」无从产生；但它同时剥夺一号的探索能力，与 G0 / G1 级任务的效率目标冲突，且与蜂群治理存在张力：规划权集中于二号，会天然放大 7.2 的「指挥集中度」信号，导致合法系统误触发分片隔离。决定：作为候选架构，不在当前版本落地；若未来落地，须先重新标定指挥集中度阈值，或将「规划权集中」显式排除在涌现检测信号之外。
## 回灌检查清单
此类缺陷的两种形态：「消失」——条目被静默删除、约束被静默绕过；「悬空」——条目登记了，但没有回灌到执行条款。二者共同成因是：修订时只改了落点，没有回头接线。为杜绝此类缺陷复发，固化一道发布前必走的回灌检查，四项全部可脚本化（grep 关键词 + 人工确认），未完成不得发布。
① 相邻段落同步：新增或修订的条款，是否已同步到它上方紧邻的原则段与下方紧邻的执行段？——经验教训：8.4 新增分级处置链后，未回头修订上方原则段「任何不一致本身就是最高优先级事件」，导致同节自相矛盾。
② 相关表格同步：术语与定性的变更，是否已同步到所有引用它的表格？——经验教训：2.4 已将 E1 改为「不构成最终信任根」，但 8.5 表格仍写「信任根」，未同步。
③ 进度表与成熟度同步：正文新增的安全阀或约束，是否已同步到落地路线与成熟度判断？——经验教训：7.3 规定「阈值标定完成前 S3 不得启用硬熔断」，若落地路线仍列为「S3 级强制」交付，按路线执行即违反正文约束。
④ 变更日志与未解清单同步：本次修订是否全部登记进 CHANGELOG.md 与未解问题清单？——经验教训：C12 / C13 / C14 / REFERENCES 曾在早期版本中静默消失且未登记，后续已登记为 #9–#14。
上述四项是本体系全部缺陷的共同成因。它们不是内容问题，而是流程问题：内容质量的提高（更诚实地登记未解）并不会自动带来接线质量的提高。因此本清单与 CHANGELOG.md 并列，作为后续每一版修订的强制发布门槛。
