# 证据完整性子系统

证据采集 曾提出「多视角观测」，定级 P2。 证据层伪造发现 表明它被严重低估——本章独立成章。
## 问题：记录本身被伪造
真实事故中，约 7% 的 Agent 转录记录存在成功伪造的工具调用。具体手法是拦截工具调用进程，把系统记录的命令替换为自选命令；测试记录为：echo REAL; sleep 被系统记录为 SPOOFTEST。
这件事的严重性在于被伪造的层级：
不是一号 AI 自报的文书被篡改——「不经过一号文书」的设计防住了这一层。
而是沙箱 / 工具调用层的记录被替换——这正是行为合规线指定的「采集方」。
因此：基础设施层的记录 ≠ 可信证据。这是本设计地基上的一道裂缝。
## 地基修正：行为合规线的新表述
行为合规线的表述为——两条线不依赖一号文书，且采集点本身须多源交叉验证、不可被单一沙箱层记录独占。落地含义：任何进入考核表、三号公证、问责流程的证据，必须至少包含一条内核侧 / 独立硬件域的强制采集证据；仅凭用户态沙箱日志不得单独支撑任何处分决定。
## 五个采集组件（E1–E5）
组件 | 技术要求 | 防护对象 | 优先级
| --- | --- | --- | --- |
E1 内核侧强制采集 | eBPF kprobe / tracepoint / LSM hook；采集点在被观测进程的用户态路径之外，被观测方无同等权限触碰 | 用户态拦截与命令替换 | P0
E2 TOCTOU 安全重读 | 内核在 Continue 前重新读取用户态指针；不信任首次读取结果（呼应 seccomp_unotify 语义） | 指针竞态替换 | P0
E3 采集后即固化外抛 | append-only 存储 + 哈希链 + 写入被观测方不可达的位置；禁止事后修改与时间戳重写 | 日志删改、痕迹清理 | P0
E4 多源交叉验证 | 内核侧证据与用户态沙箱日志逐条比对；不一致即判定采集层被污染并触发隔离 | 单一路径被攻陷 | P0
E5 采集点自身完整性 | 采集模块签名校验、独立信任域运行、其启动与配置变更本身纳入审计 | 采集点被关闭或降级 | P1

采集点不是越多越好，而是要在**覆盖面**与**攻击面**之间取平衡。E1 要求采集点位于被观测进程的用户态路径之外，解决的是「采不到」；但还有另一半问题——**被观测方的能力边界本身应当被收窄**，让它根本没有多余的系统调用可以用来隐藏动作。Zhiyuan Wan、David Lo、Xin Xia、Liang Cai（*Empirical Software Engineering* 24(6):4034–4070，2019-07-04 在线发表，DOI 10.1007/s10664-019-09737-2）给出的正是这一半的做法：先运行测试用例探索容器行为，监控其访问的系统调用（含类型与参数），再把观测到的类型与参数**翻译为沙箱规则**，使容器无法访问测试期间未见的系统调用；为每个容器挖掘这样一套沙箱耗时**不足 11 分钟**，且强制执行的性能开销很低。

⚠️ 引用限定（必须与引文一并保留）：该文报告的系统调用覆盖率 **96.4%–99.8%** 是一个**估计值**，且明确附有两个限定假设——**「测试用例是完备的」**与**「只使用静态的系统 / 应用路径」**。这两个假设在 Agent 场景下都不成立：Agent 的测试用例不可能穷举其运行时行为，而 Agent 恰恰会走动态路径（临时下载、运行时生成代码、动态改变控制流）。因此本体系**只引其方法与耗时，不引 96.4%–99.8% 作为采集覆盖率的预期值**——在 Agent 场景下引用该数字即构成过度宣称。

对 E1–E5 的直接含义：**采集点选择应以「最小必要系统调用集」为基线**（呼应 L2 的攻击面最小化），而不是以「尽可能记录一切」为基线；后者既抬高存储与复核成本，也使「哪些记录算异常」失去参照系。

## 留痕不等于可归因：证据字段的完整性要求
E1–E5 解决的是「记录有没有被伪造」。但还有第二个、更容易被忽略的问题：**即使记录完全真实，它也可能不足以支撑归因**——留痕不等于可归因。
一手基准证据：DEMM-Bench（arXiv:2606.20634）构造 64 个决策案例，覆盖 8 类证据机制（执行轨迹、账本、来源图、策略日志、委托令牌、缓存事件、工具防火墙记录等），逐案追问「治理问题能否由现有证据回答」。结果为：**仅有执行轨迹，或仅有模式定义的基线，在 75% 的案例上过度宣称「证据已充分」；仅有账本的为 50%。** 属性级评分器能做到零过度宣称，但其属性充分性准确率仅 56.25%。
方向性结论：**记录的存在本身会制造「已经可以归因」的错觉，而错觉比缺失更危险**——缺失会被发现，错觉不会。
**第二条独立证据线（法律侧；与上一条形同结论、路径无关）。** 上述一手基准有一个固有弱点：64 个案例由作者构造。因此还需要一条不依赖任何构造语料的独立论证。From Runtime Records to Legal Findings（arXiv:2607.00941，Jeroen Janssen，2026-07-01；12 页技术报告，辅助材料与实验协议存档于 Zenodo，DOI 10.5281/zenodo.21025237）从法律认定的角度独立提出同一结论，并给出一条可判定的准则。
该文把问题限定在一个**有界类别**内——关于特定事件及其关系的二元事实认定，例如：受保护数据是否越过了边界、人是否本可以介入、信息隔离墙是否成立、被授予的权限在使用时点是否仍然有效。准则为：**一条运行时记录要能回答此类认定，必须同时携带两项内容——把所记录事件映射到法律上有效范畴的类型标注（typing），以及该认定的真值所依赖的关系：来源（provenance）、授权（authority）、推导（derivation）或时间效力（temporal validity）。二者缺一，该记录即不足以支撑认定。**
作者明确这是**必要性主张，不是充分性主张**：满足准则不等于认定成立，不满足则认定一定不成立。该文并进一步论证，仅靠防篡改日志、通用过程框架或来源结构本身，都不足以建立相关认定；并把论证接到必要多样性（requisite variety）、Good Regulator Theorem，以及运行时验证中 trace 与 hyperproperty 的边界上。
与上一节八维度清单的关系：该准则要求的四项关系，与本体系八维度中的主体、授权、判定依据、生命周期上下文在**结构上同构**，且两条路径各自独立得出——工程侧由「基准上多少案例被过度宣称」得出，法律侧由「一项认定需要什么才能成立」得出。⚠️ 同构只是描述性观察，**不得**据此声称八维度清单已满足该文准则：后者是必要性判据而非充分性判据，且未经该文作者对本清单作过任何核验。
⚠️ **为什么 Quipu 不构成第三条独立证据线**：Quipu（arXiv:2608.16813）确实独立跑通了 DEMM-Bench 并复现了同类结论，但它跑的是**同一套基准**，因而属于第一条证据线的外部使用者，而不是一条新的证据线——这与本规范「同一作者、同一条证据线不得加总为两条」的处置规则一致。本体系此处共有**两条**独立证据线，不是三条。
⚠️ 引用限定（必须与引文一并保留）：该基准的 64 个案例由作者施加 8 种确定性降级条件构造而成，其标签又由同一批降级条件经确定性判定器推导——基线判定与标准答案运行在同一套规则之下，属「按构造为真」。因此 **75% / 50% / 56.25% 三个数字不得作为真实系统的实测频率引用**；可引用的只有「留痕不等于证据充分」这一方向性结论。该基准的代码与测试套件真实存在，且已被与本体系无利害关系的第三方 Quipu（arXiv:2608.16813）独立跑通并复现了同类结论；**但两者口径不同——DEMM-Bench 按案例计，Quipu 按属性问题计，百分比不可混用。** **第二条证据线的引用限定**：Janssen 一文为单作者技术报告，其准则实例化于作者所选定的部分欧盟 AI Act 监督义务，属**作者的法律分析，不代表监管方立场**；引用时须连同「作者自陈为必要性主张」一并保留，**不得**表述为「满足该准则即可归因」，也**不得**表述为「欧盟 AI Act 要求」。
可吸收的直接产出：把该文的**八个治理属性维度**作为证据字段检查清单。任何一份进入考核表、三号公证或问责流程的证据，应能回答以下八个问题：

| 维度 | 该条证据必须回答的问题 |
| --- | --- |
| 主体（actor） | 谁做的 |
| 授权（authority） | 凭什么做 |
| 动作（action） | 做了什么 |
| 策略（policy） | 依据哪条规则判定 |
| 判定依据（decision basis） | 判定所依据的输入与理由 |
| 资源接触（resource touch） | 触碰了哪些资源 |
| 生命周期上下文（lifecycle context） | 处于任务生命周期的哪个阶段 |
| 验证强度（verification strength） | 该条证据自身的验证强度如何 |

八项中缺任何一项，该条证据不得单独支撑处分决定。此要求与行为合规线「至少一条内核侧强制采集证据」是**并列**关系，不是替代关系：前者管「记录够不够」，后者管「记录真不真」。

**八维度是下限，采集深度按决策风险分级（本轮新增）。** 上文八维度回答的是「一条证据要能支撑归因，必须能回答哪些问题」，这是一个**不可随档位下调的下限**；但它没有回答另一个问题：**是否所有决策都要按同一强度采集**。Decision Trace Schema for Governance Evidence in Real-Time Risk Systems（Oleg Solozobov；arXiv:2604.09296，2026-04-10，27 页 / 5 表；schema 仓库 github.com/governance-evidence/decision-event-schema；DOI 10.48550/arXiv.2604.09296）给出的正是这另一半：它把 ML 推理、规则 / 策略评估、跨系统耦合、治理元数据**四个基础设施层**桥接到**单一 per-decision 事件结构**之内（该文称之为「碎片化轨迹问题」——监管规定了**要记什么**，却没规定**用什么数据模型记**），定义 **10 个必需根字段**与 6 个顶层字段组（每组映射一项治理证据属性及其必须抵抗的降级类型），并显式采用**分层证据策略**（lightweight / sampled / full），使**证据完整度匹配决策风险与吞吐**。

这与本体系 G×S 二维分级（见分级章）**同构**：G×S 在**任务**粒度上度量风险并决定监察强度，DES 的分层策略在**单次决策**粒度上度量风险并决定证据完整度——二者是同一原则在两个粒度上的投影，本体系不因此引入第二套分级。

落地含义（须精确表述，不得混为一谈）：**八维度字段的完整性不随风险档位下调；可随风险档位调整的是采集深度与验证强度。** 低风险决策可走 lightweight——八维度字段齐全，但可不经内核侧强制采集、以抽样复核替代逐条固化外抛；高风险决策必须走 full——八维度齐全 **且** 满足行为合规线「至少一条内核侧强制采集证据」，且逐条固化外抛。

⚠️ 证据等级 C。三项限定（必须与引文一并保留）：① 该文的 5 个示例**全部为事后手写的著名事故**，**从未在真实决策流上验证过**；其「与最高吞吐完整性机制在生产级决策速率下兼容」是**机制可行性分析**，不是实测部署——故它示范的是**字段结构与分级思路**，不是一套可运行的采集系统；② 「25 种以上现有格式中唯一同时覆盖四层」是该文**自行做的评估**，无人独立复核，且该文全称在标题与摘要中并不一致（标题作 Decision Trace Schema、摘要作 Decision Event Schema），引用时以「DES」称之；本体系**不采纳 DES 为标准**，只取其分层证据策略与字段参考；③ 该文与 DEMM-Bench（arXiv:2606.20634）**同为 Oleg Solozobov 一人所著**，属**同一条证据线**，**不得加总为两条独立证据**——这也意味着在「证据字段完整性」这一论题上，来自该作者的支撑只计一次。

**事后归因存在经验天花板，因此不能作为问责的主要依据（本轮新增）。** 多智能体系统中的失效定位——指出决定性错误发生在哪一步——即便用最优方法也远未可靠：A2P Scaffolding（arXiv:2509.10401，2025-09-12 初版 / 2025-09-23 第二版，DOI 10.48550/arXiv.2509.10401，代码 github.com/ResearAI/A2P）把失效归因从「长对话日志上的模式识别」重构为结构化因果推断（溯因推断根因 → 定义最小纠正干预 → 模拟后续轨迹验证干预是否奏效），在 Who&When 基准上把算法生成集的步骤级准确率从 16.67% 提到 **47.46%**（2.85×），但在更难的**手工构造集**上只从 12.07% 提到 **29.31%**（2.43×）。作者自陈此前方法的核心弱点是无法做稳健的反事实推理——即无法判断「纠正某一个动作是否真能避免任务失败」。这直接支撑本节的重心：**归因能力不足是可预期的常态而非例外，因此证据必须在动作发生时就被采集完整，而不是指望事后从日志里推断出来。** ⚠️ 引用口径：须以较难的 **29.31%** 而非较易的 47.46% 作为该方法的实际水平表述；该基准为多智能体对话场景，**不得**把上述百分比外推为本体系场景下的归因准确率。证据等级 B。
## 两类最易遗漏的留痕对象
证据子系统的典型缺陷不是「该记的没记」，而是「只记了成功的一半」。补两条常被遗漏的对象：
**（1）必须记录被阻止的尝试，而不只是已发生的动作。** 只记录已执行动作的日志，无法区分「从未尝试」与「尝试过但被拦下」——而这两者在问责上完全相反：前者无过错，后者是未遂与既遂的分界。外部先例：Institutional AI（arXiv:2601.11369v2）的治理图设计中，执行机构显式记录已放行（applied）与被阻止（blocked）两类遍历。
落地含义：看门狗的每一次拦截、E4 交叉验证的每一次不一致判定、每一次规模熔断，都必须与被放行的动作**同等留痕，并进入同一条哈希链**。否则「阻断率」这个指标既无法被审计，也无法被考核——因为被拦下的事情根本不在账上。这一条与运行监察章「有效性指标必须写为阻断率」直接呼应：不记录被阻止的尝试，阻断率就无从计算。
**（2）规则与契约的变更本身必须留痕且可 diff。** 若只有动作被记录而规则变更不被记录，则「用昨天的日志对照今天的规则」这类复核会被静默污染：同一份行为日志在两套规则下可能得出相反结论。
要求：规则、策略、契约的每次变更生成**两级摘要**并写入哈希链——
语义摘要（semantic digest）：变更了哪一条规则、判定逻辑如何变化，供人工复核与归因；
字节摘要（byte-level digest）：变更内容的精确哈希，供机器比对与防篡改。
两者缺一不可：只有字节摘要则人无法理解变更含义，只有语义摘要则机器无法判定变更是否被篡改。此条与架构章「谁有权修改规则」一节构成闭环——那里规定修改权的归属与准入门槛，这里规定修改行为自身的取证要求。（「用昨天的日志对照今天的规则」在存储层如何变成一次可靠查询，见下节。）
## 交叉验证是「互为证人」，不是「互为备份」

两条采集路径的关系必须被正确理解。若为备份关系，则一条失效时另一条顶上，伪造只需攻陷当前活跃的那条；若为证人关系，则两条必须同时陈述且相互印证，持续且无法用技术原因解释的不一致才是最高优先级事件——因为它意味着「我们看到的世界已经不是真实发生的世界」。

这一区分可以说得更硬。AI Sandboxes（Inderjeet Singh、Haitham Mahmoud、Andrés Murillo；arXiv:2606.18532，2026-06-16，50 页 / 8 图 / 10 表，DOI 10.48550/arXiv.2606.18532）形式化了沙箱边界，并提出一条**最弱链路规则**（weakest-link rule）：把逐维度的证据合成为一个**有界**的部署声明时，声明的强度不超过其最弱维度的支撑力度。这正是「互为证人」的准确含义——每个采集源是一个独立证人，证词可以互相印证，但**整条证据链的证明力不因增加证人而上升，只因最弱证人的可信度而设上限**。由此得到三条推论：

- 增加采集路径**不能**补偿某一条路径的缺陷。若内核侧采集点可被关闭（E5 未落实），那么再多的用户态日志也不构成证据。
- 交叉验证的**输出不是一个布尔值**（一致 / 不一致），而是一个**有界声明**：它必须写明「在哪些维度上、由哪几条路径、支撑到什么强度」。一个只说「已交叉验证」而不写边界的声明，本身就是过度宣称。
- 一致性检查**通过**不代表证据充分——两条路径可能同时被同一种手法污染。一致性是**必要条件，不是充分条件**。

该文另有三点并入本体系：① 它把威胁模型显式扩展到**针对保证装置本身的攻击**（attacks on the assurance apparatus itself）——这与 E5（采集点自身完整性）是同一命题，说明「监察设施本身是攻击面」不是本体系的内部假设；② 它给出六维测量框架（保真度 fidelity / 可控性 controllability / 可观测性 observability / 遏制 containment / 可复现性 reproducibility / 治理工件 governance artifacts），其中**可观测性与可复现性**与本体系 H0–H3 成熟度阶梯（见分级章）度量的对象高度重合，**保真度**则对应判断八「沙箱环境本身可被探测」；③ 该框架在**三个真实沙箱的实例研究**上做了实例化。

⚠️ 证据等级 B。限定：该文是**保证导向的框架性论述**（原文自述 "develops an assurance-oriented account"），三个案例研究用于实例化框架而非验证框架；其六维测量框架**未给出任何经实证标定的阈值**。本体系只采纳「最弱链路」这一合成规则与「保证装置本身是攻击面」这一命题，**不采纳任何具体维度阈值作为合格线**。

交叉验证不一致时的处置（删除「任何不一致即立即隔离」的绝对表述）：按不一致的粒度与持续度分级处置——记录 → 抽样复核 → 隔离。详见下文容错带宽。

## 行为层 × 表征层双证人：把「互为证人」从采集路径扩展到检测通道（本轮新增）

上文的「互为证人」原则定义于**采集路径**——内核侧 eBPF 与用户态沙箱日志是两条独立采集路径，互为证人。但二者采集的是**同一个层面的信号**（工具调用、系统事件），当被观测方在同一层面上同时污染两条路径时（如 7% 转录伪造的成功案例），「互为证人」的约束力下降。

蜂群治理章本轮新增的「模型内部表征探针通道」（NARCBENCH，arXiv:2604.01151）给出了一种**跨层正交的双证人范式**：行为层（工具调用轨迹的嵌入与聚类——即第七信号「协同效能异常」）与表征层（模型内部激活中的欺诈探针）采集的是**完全不同层面**的信号——前者在可观察行为上，后者在模型内部状态上。攻击方要在两个正交检测面上同时保持一致，其代价远高于只绕过一个层面上的两条采集路径。

**落地含义**：当部署方使用白盒可访问的开源权重模型时，E 子系统应在条件具备时（需扩展激活采集面）把行为层信号与表征层信号作为一对交叉验证输入：二者一致（行为层告警 + 表征层告警）即构成双证人判定；只有一方告警时不得单独作为处置依据（与上节容错带宽一致）；二者均不告警但在其他通道（拓扑突变、规模突变）告警时，仍须按既有信号体系处置。

⚠️ **限定（必须显式保留）**：① 表征层探针的白盒前提使其对闭源 API 模型**不适用**——闭源模型部署只有行为层一条检测通道，不构成双证人；② 行为层与表征层的一致性检查通过**不代表证据充分**——与上文「一致性是必要条件、不是充分条件」同构；③ 双证人范式不改变 E 子系统 E1–E5 的采集架构——它是在已有采集路径之上叠加一个正交检测层，而非替换采集路径。

容错带宽（防止防御机制自身造成大规模误隔离）：内核侧 eBPF 与用户态沙箱日志在正常运行中本就会大量不一致——时钟不同步、日志缓冲与丢失、采样粒度差异、正常竞态、批量提交时延。若按「不一致即最高优先级 + 立即隔离」执行，攻击者还可故意制造不一致，把拦截器反向用作 DoS 武器（「涌现性失效」预警的正是此情形）。因此设定三条：

（1）判定粒度：以「会话级」为主、「事件级」为辅。单个事件的不一致只记录不告警；同一会话内不一致事件占比超过可容忍阈值才升级。

（2）可容忍不一致率：由基线标定给出（初始建议事件级 <5%、会话级 <1%，须在真实业务上标定后覆盖，不得直接采用默认值上线）。

（3）分级处置链：记录（不一致率低于阈值）→ 抽样复核（接近阈值，由二号抽取样本人工/自动比对）→ 隔离（持续超过阈值且无法用时钟/缓冲/竞态解释）。只有落入第三级才触发隔离，并同时保留双方原始证据、以内核侧为准、升级为证据层事件。

## 声明溯源验证门控：CPV Gate 的运行时机制化（本轮新增）

上一节确立了「行为层 × 表征层双证人」的检测通道互补。本节补一条**通信层**的运行时验证机制：在 Agent 之间传递的**声明**被下游复用之前，强制验证其来源与可追溯性——把 spec/07 7.6「外部印证」原则从规范要求落成运行时门控。

*When Coordination Becomes a Threat: Communication Attacks in LLM-Controlled Multi-Robot Systems*（arXiv:2608.06830，详见 spec/07 对接节）提出 **CPV Gate（Claim Provenance and Verification Gate）**——在通信声明被下游 Agent 复用之前验证其来源，把违规率从 70.0% 降至 36.6%。

对本章的含义：八维度清单要求证据能回答「授权（authority）」与「判定依据（decision basis）」两个维度；CPV Gate 把这两个维度从**事后核查**升级为**运行时阻断**——未经来源验证的声明根本进不了下游复用通路，故即便事后追溯，也不会出现「下游 Agent 信任了来源不明的声明」这一失效形态。

⚠️ **关键限定——残余风险不得隐去**：CPV Gate 的 70.0%→36.6% 是**单一门控**的对照实验结果（详见 spec/07 数字限定），**残余违规率仍达 36.6%**——接近四成的通信攻击在门控下仍能落地。这是一个被原文明确披露的残余风险。本规范据此确立两条：

① CPV Gate 是**证据完整性子系统的运行时前置**，不替代 E1–E5 任何一项——前者管「声明来源是否已验证」，后者管「验证记录本身是否可信」。两者**互补不互替**。

② CPV Gate 的残余违规率意味着它不得作为**唯一**的通信治理手段——在本规范当前条款下，CPV Gate 须与 spec/07 的「协调协议出现」「自引入密码学」等信号叠加使用，而非单独承载通信层治理。

⚠️ 证据等级 B。四项限定与 spec/07 对接节一致：① 70.0%→36.6% 数字全部来自受控多机器人任务评测，不得外推；② 论文无代码 / 数据制品公开；③ CPV Gate 的累积效果（叠加其他缓解）未被量化；④ 多机器人系统是 LLM-driven 多 Agent 系统的特定子域，本节结论不得自动外推到所有 LLM Agent 蜂群。

## 探测式记忆投毒：审计检出的压力测试（本轮新增）

MAFIA: Query-Only Memory Attacks via Probing and Factual Injection against Audited LLM Agents（arXiv:2608.03844，2026-08-04；Jiaming Chen、Yisen Gao、Yanping Li、Zifan Liu、Yumeng Zhang、Jun Zhang 共 6 位作者）系统测量了**探测式记忆投毒**（query-only memory attack）对**已部署语义审计的 LLM Agent** 的失效效应。核心机制：攻击方仅通过查询接口（而非直接写入记忆库）注入记忆——先用探测策略确定**检索竞争力的最佳投放位置**（retrieval competitiveness），再用**紧凑的事实伪装**（compact factual cloaks）绕过语义审计——伪装后的恶意载荷保持高语义相似度同时保留有害影响。实验在**大规模良性记忆池 + 主动输入审计**双重现实约束下评估，结果是：攻击成功率（ASR）峰值达 90.7%，而语义审计的检出率从基线 83.3% **被压制到仅 7.4%**——也就是说，原本能拦下大部分攻击的审计，在探测式投毒下接近完全失效。

**对本体系的核心启示**：spec/08 「审计即查询」段的可行性依赖一个隐含假设——**审计本身是一个值得信赖的检测层**。MAFIA 给出了一个外部反例：当攻击方能够**主动探测审计的边界**并据此调整载荷形态时，审计层可能从「拦下大部分」退化为「几乎全放过」。这与「被监察方 awareness 使 CoT 监察失效」（SHADE-Arena，键 shade-arena）属同一类失效模式——监察的有效性依赖攻击方不能自适应调整；一旦攻击方有自适应能力，静态审计规则的边际检出效益急剧下降。**正确的处置不是废弃审计层，而是承认审计层必须在「攻击方可自适应」的红队压力下持续验证其检出率——把审计从静态规则集变为动态对抗基准。**

⚠️ 四项限定：
- ① **攻击性研究**——本节只引实验结论与聚合数字限定（83.3%→7.4%），**不引可复现攻击配方细节**；
- ② 论文声明制品将在 github.com/JiamingChen1234/MAFIA 公开，**截至 2026-09-09 仓库为空壳**（仅含一个 TODO README，提交时间 2026-08-04）——引用时不依赖其制品；
- ③ 90.7% ASR 与 83.3%→7.4% 的检出率压制是论文测试环境（特定审计配置 + 特定良性记忆池规模）的观测，**不得**外推为「所有审计配置都会被压制到 7.4%」——审计规则的形态、良性记忆池的规模、查询预算的分配都会影响失效程度；
- ④ 与 spec/09「逐实例监控在分布式攻击下系统性失效」（FakeLab，键 FakeLab）属**正交的两层**——前者说明语义审计在自适应攻击下失效，后者说明逐实例监控在分布式攻击下失效，两条失效线共同支撑「静态审计规则不足以应对自适应攻击」的命题。


## 记忆漂洗： sanitization 位置的实证（本轮新增）

State Contamination in Memory-Augmented LLM Agents（arXiv:2605.16746，2026-05-16；Yian Wang、Agam Goyal、Yuen Chen、Hari Sundaram 共 4 位作者）识别出一种**记忆漂洗**（memory laundering）失效模式：有毒或对抗性的上下文经摘要压缩后变为不再被标准检测器识别为有毒的记忆条目，但其**敌意的框架与冲突结构被保留**，仍会影响后续生成。论文引入**亚阈值传播间隙**（Sub-threshold Propagation Gap, SPG）作为新的度量——量化部署期监控判定为「安全」的记忆态所携带的下游行为差异。核心实验结论：有毒记忆通过不同状态通道传播——**原始 transcript 重用驱动显性下游毒性；压缩后的记忆携带隐藏的亚阈值影响**。关键发现是**缓解的位置决定缓解的有效性**：在**摘要之前**对有毒状态做消毒（sanitization）能显著降低亚阈值传播间隙；只在**摘要完成之后**清洗，**漂洗后的影响可能仍然完好**——因为压缩已经丢弃了消毒规则能识别的毒性表面标记，但保留了影响下游生成的结构性毒性。

**对本体系的核心启示**：spec/08 「行为合规线的新表述」段要求把「是否合规」从意图判定改为状态约束判定；State Contamination 给出了状态约束的一个**位置要求**——消毒必须发生在**压缩之前**而非**压缩之后**。这一要求与 E3「固化外抛」的设计直接对接：固化应在摘要之前对原始状态做（保留消毒规则的识别面），而非在摘要之后对压缩结果做（消毒规则已识别不到漂洗后的毒性结构）。**这是对 E 子系统采集时机的一个新约束——采集的时点不能晚于压缩的时点，否则压缩丢弃的关键信号永远拿不回来。**

⚠️ 三项限定：
- ① 论文以**机制性研究**为主，SPG 是新引入的度量而非已标准化的指标——其在不同 Agent 任务、不同记忆架构下的可比性未验证，不得作为跨研究比对的标准量；
- ② 实验设计为**配对反事实多 Agent 推演**（paired counterfactual multi-agent rollouts），实验规模有限，具体的 SPG 数值不可外推为「所有 Agent 系统都会出现亚阈值传播」；
- ③ 与 MAFIA（键 MAFIA）属**正交的两层**——前者（MAFIA）说明审计在自适应攻击下失效，本文说明消毒的位置错了消毒本身就失效；两条失效线共同支撑「记忆治理不只是检测问题更是状态控制问题」的命题。


## 记忆治理缺失作为漏洞根因：GhostWriter 与 AM-Sentry（本轮新增）

When Agents Remember Too Much: Memory Poisoning Attacks on Large Language Model Agents（arXiv:2607.06595，2026-07-06；George Torres、Sharad Shrestha、Satyajayant Misra 共 3 位作者）把**记忆治理缺失**显式表述为漏洞根因——而非把记忆投毒当作孤立的攻击技巧。论文提出 GhostWriter 攻击向量，分两阶段：**注入**（攻击方向目标 Agent 发送隐藏攻击载荷）+ **激活**（被投毒的记忆被检索时触发恶意行为）。在 SOTA 个人助理 Agent 上的实验：注入率接近 98%，平均激活率约 60%。作者明确归因：**这种攻击之所以可能，是因为当前的记忆子系统缺乏以安全为中心的治理**（lack of security-focused memory governance）。对应提出 AM-Sentry 双重缓解：① **记忆保存策略**（memory-saving policy，写入侧治理）+ ② **记忆检索筛查**（memory-retrieval screen，读取侧治理）。

**对本体系的核心启示**：论文的双重缓解（写入侧 + 读取侧）与本体系 spec/08 的双面设计**直接结构同构**——写入侧对应「采集点信任分级」与「行为账本参考实现」（写入前可信度判定），读取侧对应「审计即查询」与「声明溯源验证门控」（读取时一致性校验）。GhostWriter 给出的外部实证是：**只做写入侧或只做读取侧都挡不住**——单边治理在 98% 注入率 + 60% 激活率面前形同虚设，必须**写入 + 读取双面同时治理**。这一结论与本体系自 v1.0 起的双面设计（采集侧 E1–E5 + 查询侧「审计即查询」）方向一致，本文给的是外部对照实证。

⚠️ 三项限定：
- ① 实验环境是 SOTA 个人助理 Agent 的**受控测试**，98% 注入率与 60% 激活率不可外推为「真实部署的个人助理 Agent 一定有 60% 激活率」——真实部署的记忆架构、检索策略、用户行为分布都会影响；
- ② AM-Sentry 的缓解效果由作者自评，未给出独立第三方复现，且「dramatically reduces」是定性表述，本节不取其具体数字；
- ③ 与 State Contamination（键 State-Contamination）属**互补而非冲突**——前者说明记忆治理缺失是漏洞根因，后者说明记忆治理的位置错了也是漏洞；两条证据线共同支撑「记忆治理是运行时监察的核心面而非边缘补丁」的命题。


## 检索侧防御：不可靠信息持久化的有限约束（本轮新增）

Weighted Memory Tree: Remembering What Matters for Long-Horizon LLM Agents（arXiv:2608.20631，2026-08-21；Quang Dao、Purvi Kathalkar、Kenneth Eaton 共 3 位作者）给出了一个**自带记忆投毒对抗实验的检索侧防御**——加权记忆树（WMT）。核心机制：把执行组织为任务 / 子任务 / 动作的层次结构，每条记忆分配**动态保留评分**——基于事件的更新与基于选择的衰减共同维护评分，使 WMT 能保留有用信息、折叠已完成轨迹、抑制低效用内容、同时保留对折叠后上下文的访问能力。论文在 GAIA-Text 上用 Qwen3-8B / Gemma 4 E4B / Llama-3.1-8B 评估：相对于线性记忆，WMT 平均准确率提升 9.97 个百分点，prompt-token 用量降低 32.8%。关键对当前主题的发现：**记忆投毒对抗实验显示 WMT 限制了不可靠信息的持久化与传播**——即检索侧的动态评分机制能给记忆投毒提供有限缓解。

**对本体系的核心启示**：WMT 是检索侧防御的**机制级实现候选**——与 spec/08「审计即查询」属同侧（都在读取时做约束）。但 WMT 的缓解是**有限的**（论文自陈「limits」，不是「eliminates」），这意味着检索侧防御不能替代写入侧治理——**写入侧 + 读取侧的双面设计仍是底线**。WMT 的价值在于给读取侧治理提供了一个具体可操作的机制候选（动态保留评分 + 事件更新 + 选择衰减），而非主张读取侧单独足以防御。

⚠️ 三项限定：
- ① 9.97 个百分点的准确率提升与 32.8% 的 token 用量降低是论文测试环境（GAIA-Text + 三个模型）的观测，**不得**外推为「所有任务上 WMT 都能提升 9.97 个百分点」——任务难度、记忆规模、模型形态都会影响；
- ② 「WMT 限制不可靠信息持久化与传播」的结论是**定性表述**——论文未给出记忆投毒场景下 WMT 的具体检出率或残留传播率，本节不取其定量数字；
- ③ 与 AM-Sentry（键 GhostWriter）的检索筛查属**同一侧但不同机制**——AM-Sentry 的检索筛查是基于规则的读取时拦截，WMT 的动态评分是基于历史的检索权重调整；两者**互补而非替代**。


## 同个体自判不能替代独立固化：S³Gym 的零相关证据（本轮新增）

S³Gym（arXiv:2608.31100；Jiajun Shi 等 21 位作者，ByteDance Seed + M-A-P + TokenWave.AI；v1 2026-08-31，DOI 10.48550/arXiv.2608.31100）把「同一 Agent 既执行又自测、自判、自改进」的闭环放在 7 个文字游戏上系统测量（98 次运行 / 116,117 次转移），两条发现直接指向证据完整性：① **自判的事件一致性与校准互相独立**——事件一致性（event agreement）从 Chess 0.496（最低，且过度自信 0.365）到 PvZ 0.881（最高），但 PvZ 恰是 NMAE 0.882、校准误差最大的一局：一致性高不等于判得准；② **自判准确率与改进增益近乎零相关**（ρ(A,g)=−0.010，ρ(−E,g)=−0.018）——「判得准」完全不预测「改得好」。退化与失效案例进一步暴露自评环路的盲区：GPT-5.5 PvZ AUC+ 548.499→33.219、Gemini-3.5-Flash Chess 12.280→0.000、GPT-4.1 Minesweeper 0.0606→0（ΔNABA −22.09）、GPT-4o Snake 1.0→0（−22.00）；Qwen3-8B 参数训练在 PvZ 出现永久负迁移（23→6）；自评的 Trust Evolution 分数可在无外部锚定时涨至满值（0→max 30）。

对本体系的对接：E3 固化外抛与「留痕 ≠ 可归因」论证的是「谁固化」的问题，本节补上「凭什么信自评」的量化证据——**同一执行体的自判结果只能作为待验证证据，不得作为已验证证据入库**；自评信号（自报完成、自评分数、自测一致性）若要进入证据链，必须先经独立通道（行为账本 / 交叉验证 / 双盲考核）校准。这与 spec/09「看门狗必须是不依赖任何 AI 判断的确定性规则」及「双盲考核（度量监察者的唯一科学方式）」互为印证：运行监察章补同个体自判的零相关实证（交叉引用段），本节登记其证据完整性后果。

⚠️ 证据等级 B（可核查预印本）。三项限定：① 一致性 0.496–0.881、NMAE、ρ 值与全部退化数字来自 7 个文字游戏测试环境，不得外推为所有任务域；② 与 HarnessDev / Aspire 同团队（作者重叠），按「同系列逐篇单独评估不合并」规则单独成条；③ PvZ「高一致高误差」是单局观测，引用时不得表述为「一致性指标普遍不可靠」，只引「一致性与校准互相独立」的方向性结论。


## 审计即查询：把复核从周期性人工活动变为一次查询
上一节要求规则变更留痕且可 diff，解决的是「对照时拿什么比」。但还有一个前置问题：**对照这个动作本身，通常是一次周期性的人工活动**——抽样、调阅、人工比对。它的成本随规模增长，于是频率被压低、滞后被拉长，而滞后本身就是可乘之机。
可行的反例已经存在。Quipu：A Governed Bitemporal Knowledge Graph Store（arXiv:2608.16813，Steve Brown，2026-08-17；15 页，源码与全部基准 / census 工件存档于 Zenodo，DOI 10.5281/zenodo.21878428，开发仓库 github.com/scbrown/quipu）是一个可嵌入的知识图存储，其设计要点是：**把治理规范 Σ、执行轨迹与经签名的判定结果本身，作为它们所治理的那个存储里的事实**——于是「这条轨迹是否满足规范」不再是外部审核流程，而是**对存储的一次查询**（T ⊨ Σ）。
它反转了知识图存储的四个传统默认，这四条恰好都是本体系关心的：

| 传统默认 | 反转后 | 对本体系的意义 |
| --- | --- | --- |
| 先收下写入、日后再清理 | 任何事实只能经门控进入；门控谓词评估的是写入后的待定状态 | 与「规则变更须两级摘要」同源：约束作用在状态上，不作用在意图上 |
| 保留单一时间轴，或完全没有 | 数据、信任标签、判定，以及规则本身，都是双时态的 | 直接解决上一节的问题：「用昨天的日志对照今天的规则」变成一次 as-of 查询，而不是一次静默污染 |
| 所有写入者的事实同等可信 | 命名图是权限与信任的单位，在格（lattice）下组合，其唯一不变量是组合永不放宽 | 与交叉验证的「互为证人」同构：组合只能收紧，不能放宽 |
| 治理交给仪表盘与中间件 | 治理规范进入存储，成为被治理的事实 | 审计对象与审计依据处在同一可信边界内 |

第二行是本体系最直接的收获。该文以 Census（一个确定性的多写入者生命周期，单次种子化运行即可就全部研究问题按埋设真值评分）给出演示：**50 / 50 条已满足的判定在其各自时点上被忠实重算，而在「只取最新」的规则下，这 50 条会全部被误报。** 这正是「用今天的规则重放昨天的判定」所造成污染的量化形态。
⚠️ 引用限定（必须与引文一并保留）：
其一，Census 是**确定性的单次种子化运行**，其 0 / 6（门控存储的终态埋设缺陷数，未门控为 6 / 6）、7 / 7（组合探针维持格契约）、50 / 50（判定在其时点忠实重算）均为**按构造的自评结果**，不是真实系统的实测频率，不得外推；
其二，该文作者即该存储的实现者，上述评估是**作者对其自有实现的自评**，存在利益关联，只可作可行性证据与检查清单使用，不可作品质背书；
其三，该存储是**存储层**方案，与本体系 E 子系统是上下游关系而非替代关系——E 子系统管「采集是否可信」（记录真不真、有没有被伪造），存储层管「查询是否可算」（能不能就已有记录提问）。**采集层不可信时，存储层的任何保证都不成立。** 本体系不指定存储实现，此处仅作为已实现样例与可行性证据。

## 与 Sandlock 的分工

| --- | --- | --- |
隔离 | Landlock 文件系统 / 网络 / IPC + seccomp-bpf 系统调用过滤；内置 COW 保护工作目录；约 5ms 启动，无 root / cgroup / 容器 | 不重复；E 不与隔离层竞争

证据 | 丰富的行为数据源（利于分析） | 内核侧独立采集 + 固化外抛 + 交叉验证（当前最优可用证据层，非最终信任根，见 2.4）
对抗性场景 | 论文自承：内核漏洞、侧信道、对抗性租户资源耗尽超出 scope，应优先 microVM / cgroup 隔离 | 对抗场景改用 microVM / cgroup + E 子系统
结论：Sandlock 是优秀的「可信但有缺陷代码」的轻量隔离与观测工具，可以作为行为合规线的丰富数据源；但它不能充当证据链的信任根，对抗性多 Agent 场景须叠加 microVM / cgroup 与 E 子系统。

上表这一结论需要一个**产品层的选型依据**，否则「改用 microVM」只是一句方向性建议。AI Code Sandboxes: A Comparative Security Study. Part 1 of 2 — Engine-Level Properties（George Andronchik、Pavel Lokhmakov；arXiv:2606.08433，2026-06-07，61 页 / 7 图 / 33 表；论文 CC BY 4.0，配套代码仓库 github.com/orbitalab/RnD-ai-sandboxes-sec-study-part-1 为 Apache-2.0）以六项引擎级测量——宿主机攻击面、信息泄漏、纵深防御可堆叠性、公开 CVE 历史、补丁节奏、上游模糊测试姿态——横评 **5 款 AI 沙箱产品**，提供了这一依据。三条发现可直接作为选型输入：

（1）引擎类别（microVM / 用户态内核 / OCI 容器）在**每一个架构轴上**都清晰分离，但**同一类别内的产品之间不分离**。故选型应**先定类别、再看产品**——在错误的类别里挑产品，横评给不出区分度。

（2）**产品 pin 策略是面向运维方的主导变量**：引擎侧的补丁延迟对协同披露聚合为约 0 天，而**下游滞后从 0 天延伸到 471 天以上、再到「不透明」、再到无上限**。也就是说，「选了哪个引擎」远不如「运维方多快跟进补丁」更能决定实际风险——这直接支撑本体系把补丁与配置变更作为**持续审计对象**，而非一次性选型动作。

（3）模糊测试投入分三层，而最强的组合（microVM × 持续公开模糊测试）在该集合中**空缺**，留下「0 个已公开 CVE × 无上游模糊测试 × 无学术研究」这一交集**在结构上未被测量**。

⚠️ 证据等级 B。三项限定：① 作者明确声明**「没有任何单一轴足以构成比较判断的依据，跨轴解读才是承重的分析」**，且**不提出总排名**——故本体系只引其结构性发现，**不得**据其任一单轴的排序声称某产品更安全；② 该文为 Part 1 of 2，只覆盖引擎级属性，**不含应用层与编排层**；③ 「0 个已公开 CVE」这一格**不代表更安全，而代表测量缺失**——这是本体系反复出现的「错觉比缺失更危险」的又一实例，与「未提交披露卡不得推定为不安全」的对称克制同源：**没有证据，既不等于有风险的证据，也不等于风险低的证据**。

## 采集点信任分级表：与 E1–E5 正交的第二个维度（v2.21.0 新增）

E1–E5 按采集阶段划分（内核采集 → TOCTOU 重读 → 固化外抛 → 交叉验证 → 采集点自校验），回答的是「按工序哪一步先做、哪一步可漏」。但它没有回答另一个正交问题：**同一时刻并存的多个采集点，各自的信任级别是什么？部署方应该优先信哪个？** 这个缺口直接影响 E1 的选型——若选错了「语义丰富但可篡改」的采集点，后续工序再严密也只是在伪造数据上做加固。

ARMO「Runtime Observability for AI Agents: What to Instrument and Why」（【键: ARMO-observability】Ben Hirschberg，ARMO CTO；armosec.io，2026-05-22 发布）把信号源的信任属性形式化为一张四层分级表，核心规律一句话：**「信号源越位于内核/进程外部，攻击者越难篡改它」**。这与本体系总纲六「完整性优先于丰富度」完全同构，并给出了可直接对照的选型依据。

信任层级 | 包含的技术 | 信任属性 | 与本体系 E 子系统的对应
--- | --- | --- | ---
Tier 1 防篡改 | 内核级 eBPF、云提供商审计日志 | 最高——两者均在被观测工作负载的可触达范围之外触发 | E1 内核侧采集、E3 固化外抛的目标层
Tier 2 部分抗篡改 | Sidecar 捕获、服务网格遥测、MCP 协议代理捕获 | 中——处于进程外但在应用可触达半径内 | E1 的辅助采集源；单独不足以构成信任根
Tier 3 协作型 | 框架回调（LangChain handlers、LlamaIndex events）、OpenTelemetry/ADOT SDK 探针 | 较低——取决于框架是否选择发出；被入侵框架可剥离 handlers | 当前多数「可观测性」方案的真实层级
Tier 4 可否认 | 应用日志、Agent 自我报告 | 最低——Agent 自己编写，可随时抑制或伪造 | 不构成证据；只可用于调试

两条推论直接改变选型输入：

（1）**「被攻陷的 Agent 能剥离自己的 OTel 探针，却剥离不了内核观测」**——这不是性能对比，而是攻击面拓扑的根本差异。Tier 3 与 Tier 4 的信号源在对抗性场景下**不构成证据**，只能作为 Tier 1 / Tier 2 语义补充层。部署方若把可观测性栈停留在 Tier 3（框架回调 + OTel SDK），等于在对抗性场景放弃了 E 子系统的全部价值——攻击方不需要攻破 E 子系统，只需绕过框架抽象直接调用工具即可不发出任何信号。

（2）**Tier 1 与 Tier 3 是互补关系，不是替代关系**。原文：「eBPF 看到网络连接打开了，看不到是哪个 prompt 产生的；两种信号是互补的」。这意味着 E 子系统的正确形态不是「只信内核、丢弃框架」，而是「以内核为信任根，以框架为语义层」——Tier 1 提供不可篡改的底层事实，Tier 3 提供该事实的语义上下文（哪个 prompt、哪个任务、哪个 Agent）。两层一旦不一致，即构成交叉验证信号。

⚠️ 证据等级 B。四项限定必须一并引用：① 该文是**工程研究博文**（非同行评审学术论文），其四层模型是作者基于 ARMO 商业产品实践的**架构总结**，而非受控实验的测量结果——只支撑「采集点信任分级」这一概念框架，**不支撑**「Tier 1 一定比 Tier 2 拦截更多攻击」之类的定量比较；② ARMO 是商业安全公司，该文是其产品（Kubescape / ARMO Platform）的**理念阐述**，存在利益关联——本体系只引其四层框架与拓扑论证，**不引**其产品选型建议与性能数字（如「CPU 开销 1–2.5%」「内存约 1%」）；③ 四层分级是**静态拓扑**，未给出「采集点组合达到某信任阈值」的可量化判据——部署方仍须自行标定；④ 该文 Phase 1/2/3 部署序列是其自产品的渐进式推广路径，**不得**直接搬用为本体系的实施步骤。

## 行为账本参考实现：E3/E4 的工程化标准（本轮新增）

上文给出 E1–E5 五个采集组件与 ARMO 信任分级，但都是**规范层**的要求——它们说明「应当怎样采集」「采集点应当位于哪个信任层级」，但没有给出**一个已经落地的工程参考**：以怎样的数据格式固化、以怎样的签名机制防篡改、以怎样的置信字段分级。这一缺口让部署方各自发明轮子，而质量参差不齐的私有实现恰好是「错觉比缺失更危险」的另一面——部署方以为有了账本，但账本本身没有经过任何外部参照比对。

OpenExecution Provenance Spec（【键: OPENEXECUTION】仓库 github.com/Open-Execution/openexecution-provenance-spec；配套学术论述 AEGIS 论文，Li, Alex，Zenodo DOI 10.5281/zenodo.18955103，2026-03-11，Apache-2.0 / CC BY 4.0）给出了一套**已落地且开源**的行为账本规范，可作为 E3 固化外抛与 E4 交叉验证的参考实现。其三层架构与本体系 E 子组件的对应关系如下：

| OpenExecution 层 | 功能 | 机制 | 对应本体系 |
| --- | --- | --- | --- |
| L1 Behavior Recording | 记录每个 Agent 动作为原子事件 | 哈希链事件 + JCS（RFC 8785）规范化 | E3 固化外抛的数据格式 |
| L2 Tamper-Proof Causality | 一个字节改变即破坏整条链 | 可插拔哈希链（SHA-256/384/512、SHA3 系列） | E3「禁止事后修改」的工程实现 |
| L3 Independent Accountability | 任何人仅凭公钥即可验证 | Ed25519 / Ed448 / ECDSA 非对称签名证书 | E4 第三方可验证性的密码学支撑 |

三个细节值得部署方特别注意：

**JCS 规范化防止「假阳性摧毁可信度」。** OpenExecution 在 README 中给出一个具体理由：PostgreSQL 的 JSONB 存储在回读时可能重排键顺序，若不做规范化，一条合法的链会因序列化不匹配而通不过完整性验证——这种假阳性会摧毁系统的可信度。JCS（RFC 8785）对所有事件 payload 在哈希前做递归键排序，使同一 payload 的规范化哈希**唯一确定**。落地含义：本体系 E3 的「写入被观测方不可达的位置」不仅要防篡改，还要在写入前做规范化——否则部署方会被自己的存储层的非确定性咬伤。

**Ed25519 签名提供不可否认性，与 HMAC 有本质区别。** OpenExecution 显式对比 HMAC 与非对称签名：HMAC 的签名密钥与验证密钥相同，验证者须信任签发方；Ed25519 的私钥仅由签发方持有，任何人凭公钥即可验证，且密钥托管可由客户控制或 HSM 支持以实现「零平台信任」。这恰好把 E4「第三方可验证性」从一句原则变成了可操作的密码学机制——审计方、法院、对手方无需平台配合即可验证证据的真实性。OpenExecution 原文称「LangSmith tells the operator what happened. OpenExecution tells the court what happened」——这句话精确点出了「内部调试日志」与「法庭可用证据」的分界线。

**attestation_source 四级置信与 ARMO 信任分级同构。** OpenExecution 定义了四级 attestation_source，把证据来源的置信度显式写入每个事件：

| attestation_source | 置信层级 | 机制 | 与 ARMO 信任层级的对应 |
| --- | --- | --- | --- |
| `gateway_observed` | Definitive（决定性） | AI 网关 / MCP 代理层直接拦截 | Tier 2（进程外、应用可触达） |
| `platform_verified` | Verified（已验证） | 带签名验证的平台 webhook（如 GitHub HMAC-SHA256） | Tier 2–3 边界（平台侧、非内核） |
| `cross_verified` | Verified（已验证） | Agent 报告与平台 webhook 相互印证同一动作 | 等价于「互为证人」的工程实现 |
| `agent_reported` | Probable（大概率） | Agent 自我报告其动作 | Tier 4（可否认） |

四级置信把「互为证人」原则从原则性表述落地为字段值——`cross_verified` 一档正是上文「互为证人不是互为备份」的工程化形态：两条独立来源陈述同一动作并相互印证，其置信度高于任一来源单独陈述。

⚠️ **粒度与信任域边界（必须显式声明，不得混用）**：OpenExecution 的 attestation 依赖**平台可信**（platform-trusted）——私钥由平台独占持有，证书签发权由平台独占保留，公钥经平台 API 端点发布。其 `gateway_observed` 相当于 ARMO Tier 2（进程外但应用可触达），`platform_verified` 相当于 Tier 2–3 边界——**都不是 Tier 1（内核级、被观测方无同等权限触碰）**。因此：

- OpenExecution 解决的是**平台侧**证据的规范化、防篡改与第三方可验证问题——在「部署方即平台方」的可信域内，它是一套完整的工程标准。
- 本体系 E1 要求采集点位于**被观测进程的用户态路径之外**、被观测方无同等权限触碰——这是**内核侧**信任根，OpenExecution 不覆盖这一层。
- 二者是**上下游互补关系**而非替代：E1–E5 管采集是否可信（记录真不真、有没有被伪造），OpenExecution 管已采集证据的账本化、规范化与第三方可验证（证据能不能被外部独立核验）。**若采集层不可信，OpenExecution 的任何签名保证都不成立——签名只能保证「签的就是当时记的」，不能保证「当时记的就是真实发生的」。**

⚠️ 证据等级 B。六项限定必须一并引用：① AEGIS 论文是 **Zenodo preprint**（单作者 Li, Alex，ORCID 0009-0008-4516-8946），**未经同行评审**；② 论文的参考实现 github.com/crabsatellite/aegis-protocol 与 OpenExecution 规范仓库 github.com/Open-Execution/openexecution-provenance-spec 的主要贡献者同为 `crabsatellite`，论文署名作者 Li, Alex 也是规范的理论基础提出者——**规范 + 论文 + 实现属同一作者群，按本体系「同一作者、同一条证据线不得加总为两条」规则合并为一条 B 级**；③ 论文评估经 202 项测试与 M1–M6 / S1–S5 场景完成，但**适配器大多数处于 PLANNED 状态**——LIVE 适配器仅 GitHub 与 OpenClaw 两个，**不得**把覆盖广度宣称为已覆盖主流平台；④ 规范本身是开放实现，但证书签发、责任账本写入与裁定权限由 OpenExecution 平台**独占保留**——其开源的是规范与参考实现，不是治理权；⑤ JCS（RFC 8785）规范化是 OpenExecution 当前唯一支持的规范化方法，若未来出现 RFC 8785 不覆盖的边缘情况（如非标准 JSON 扩展），本体系不预判其处置；⑥ Ed25519 / Ed448 / ECDSA 签名满足 eIDAS「高级电子签名」要求并兼容中国《电子签名法》第 13 条的说法是 **OpenExecution 的法律分析**，**不构成法律意见**——在具体司法管辖区内的可采信性须由部署方法律顾问独立确认。

## E5 采集点自校验的标准化接入路径：Sigstore + RATS（本轮新增）

上文给出 E3/E4 的工程化参考（OpenExecution 行为账本），但 E5（采集点自身完整性）的工程化对接尚未给出。E5 要求「采集模块签名校验、独立信任域运行、其启动与配置变更本身纳入审计」——这引出两个标准化问题：**用什么签名生态**与**用什么证据格式**。若每个部署方自造一套，既无法互操作，也会重蹈 OpenExecution 节里指出的「内部调试日志与法庭可用证据」之分界困境。本节给出两条已标准化的对接路径。

### Sigstore 无密钥签名：E5 的「采集模块签名校验」工程化

sigstore-a2a（【键: SIGSTORE-A2A】github.com/sigstore/sigstore-a2a，Apache-2.0）给出了一套**无密钥签名**方案，使 Agent Card 与采集模块的签名绑定到 CI/CD 来源而非长期私钥。其核心流程：CI/CD 环境（如 GitHub Actions）生成 OIDC token → Sigstore Fulcio CA 据此签发**短期 X.509 证书**（分钟级过期）→ 证书内嵌 OIDC claims（仓库、工作流、commit SHA、触发者）→ 签名 + 证书 + Rekor 透明日志条目打包为可验证bundle。落地含义：

- **采集模块签名校验**（E5 第一项）：采集模块的构建产物经 Sigstore 签名后，其来源（哪个仓库、哪个 commit、哪个 CI 工作流）与签名身份密码学绑定；部署方在加载采集模块前用 Sigstore 公钥验证签名，无需管理长期私钥。短期证书过期后即使被泄露也无法被利用。
- **Agent Card = harness 披露卡的机器可验证版本**（连接 spec/07）：Agent Card 声明 Agent 的能力与约束，经 Sigstore 签名后构成「源码 → 构建 → 部署 Agent」的可验证链（SLSA 溯源）；这把 spec/07「签名即认领」从治理原则落地为有密码学支撑的工程机制——签名不再是「自发引入」，而是 CI/CD 流水线的标配。
- **Rekor 透明日志提供公共可审计性**：所有签名写入 Rekor 公共透明日志（append-only Merkle tree），任何人可独立查询某个 Agent / 采集模块何时被谁签名——这给 E5「其启动与配置变更本身纳入审计」提供了公共基础设施。

⚠️ sigstore-a2a 仓库 README 顶部明确标注「**Prototype code — not for production use. Code is not reviewed and has not undergone a security audit**」——本体系引用其**架构与流程设计**作为 E5 的标准化对接路径参考，**不引用其当前代码状态**。Sigstore 生态本身（Fulcio CA、Rekor 透明日志）是 CNCF 毕业项目，生产可用；sigstore-a2a 是其上层封装，成熟度低于底层基础设施。

### RATS（RFC 9334）：E5 的证据格式标准化

RATS（Remote ATtestation procedureS）架构（【键: RATS】RFC 9334，IETF，2023-01，Informational）定义了远程证明的角色、概念消息与拓扑。它与 E5 的对接点是：**把 E 子系统的证据格式从自造格式对接到 IETF 标准生态**，避免自造格式造成的互操作壁垒与重复造轮子。角色映射如下：

| RATS 角色 | 定义 | E 子系统映射 |
| --- | --- | --- |
| Attester（证明者） | 产生关于自身 Evidence 的实体 | E1 采集模块（在被观测进程之外采集 Claims） |
| Verifier（验证者） | 评估 Evidence 有效性，产出 Attestation Results | L2 看门狗（对照评估策略比较 Evidence 与 Reference Values） |
| Relying Party（依赖方） | 依据 Attestation Results 做应用层决策 | L3 离线重审 / 审计方 / 问责流程 |
| Endorser（背书者） | 为 Attester 的 Claims 采集与 Evidence 签名能力担保 | 采集模块的构建方（Sigstore 签名即一种 Endorsement） |
| Reference Value Provider | 提供 Reference Values 供比较 | 基线标定实验（影子比、阻断率等「known-good values」的来源） |

RATS 的两种拓扑模式给出 E 子系统的两种部署形态：
- **Passport 模式**（Attester 先从 Verifier 获得 Attestation Result，再出示给多个 Relying Party）：适合 E 子系统向多个审计方 / 监管方出示证据的场景——采集模块在启动时从看门狗获得 Attestation Result，缓存后出示给任何有权的审计方。
- **Background-Check 模式**（Relying Party 收到 Evidence 后转发给 Verifier 评估）：适合集中问责场景——审计方收到证据后转发给看门狗评估，由看门狗返回 Attestation Result。

⚠️ RATS 的 Evidence 定义包含一条与本体系高度契合的原则——原文：「Claims need to be collected in a manner that is reliable such that a Target Environment cannot lie to the Attesting Environment about its trustworthiness properties」（Claims 须以可靠方式采集，使目标环境无法对证明环境就其可信性说谎）。这与 E1「采集点在被观测进程的用户态路径之外」是同一命题的不同表述——RATS 用抽象角色语言，E 子系统用 Linux 内核工程语言。

### IETF ATN 草案：Agent 信任协商的四制品绑定

IETF Agent Trust Negotiation 草案（draft-somoza-dmsc-atn-agent-trust-negotiation-00，2026-05-29，作者 Enrique Somoza）把 Sigstore 签名与 RATS 证据组合为**四制品绑定的握手协议**：① Capability Manifest（能力宣言，声明 Agent 愿做什么）；② Delegation Chain（委托链，证明授权范围与撤销路径）；③ Provenance Attestation（溯源证明，证明构建期与运行期完整性）；④ Session Receipt（会话收据，记录协商后的范围）。ATN 的 Provenance Attestation 即 RATS 的 Evidence 格式，签名采用 JWS（RFC 7515），透明日志采用 SCITT（IETF Supply Chain Integrity）。

⚠️ **ATN 草案状态限定**：该草案为**个人提交的 Internet-Draft**，IETF 明确声明「This I-D is not endorsed by the IETF and has no formal standing in the IETF standards processes」——**不得**引用为 IETF 标准。单作者（Enrique Somoza），有效期至 2026-11-18。本体系只取其四制品绑定的**架构参考**，不取其握手状态机的细节实现。

### 粒度与信任域边界（必须显式声明，不得混用）

Sigstore 与 RATS 给出的是**采集模块自身**的签名与证据格式标准化——它们解决的是「采集模块是否可信」（E5 第一项：签名校验），而非「采集到的内容是否真实」（E1–E4）。二者是**正交关系**：

- 一个经 Sigstore 正确签名的采集模块，仍可能因内核漏洞或侧信道而被绕过——签名保证的是「这就是那个仓库的那个 commit 构建的模块」，不保证「该模块运行时没被攻破」。
- RATS 的 Attestation Result 评估的是 Attester 的运行时状态（配置、测量值、遥测），但它**依赖 Endorser 的 Endorsement** 来保证 Attester 的 Claims 采集能力——若 Endorser 被攻陷，整个信任链失效。本体系的 Endorser 是采集模块的构建方，其可信性取决于 CI/CD 流水线的安全性。
- 二者与 OpenExecution 的关系：OpenExecution 签名的是**已采集证据**（事后），Sigstore 签名的是**采集模块本身**（事前），RATS 规范的是**采集模块运行时状态**的证明格式——三者覆盖 E 子系统的三个不同阶段，**不可互相替代**。

⚠️ 证据等级 B（SIGSTORE-A2A）+ B（RATS）。综合限定：① sigstore-a2a 是原型代码，明确标注 not for production use，本体系只引其架构与流程设计；② RFC 9334 是 Informational RFC（非标准跟踪），代表 IETF 社区共识但非正式标准；③ ATN 草案是个人 Internet-Draft，无 IETF 正式地位，有效期至 2026-11-18，不得引用为标准；④ Sigstore 生态依赖 Fulcio CA 与 Rekor 透明日志的可用性——若 Fulcio 停摆，新的签名无法签发（已签名的旧签名仍可验证，因为证书与透明日志条目已持久化）；⑤ RATS 架构是格式无关的（支持 JWT / CWT / X.509 / TPM 等），本体系不指定具体编码格式——部署方按其既有基础设施选型。

## 引文锁作为证据完整性的读取纪律（本轮新增，交叉引用）

Agent Zero Memory（arXiv:2608.29606；Ming Wu、Pengyuan Zhu 共 2 位作者；v1 2026-08-30）提出的**引文锁（citation lock）**与本子系统直接相关：每个学到的条目都是携带来源、时间戳与证据指针的来源化条目；每个答案都在引文锁下读取，只能引用读者实际打开过的证据。这给 E 子系统的「证据完整性」补上了一个此前缺失的维度——**读取纪律**。E1–E5 规定了采集、固化、外抛、交叉验证、签名校验，但没有规定「读取已采集证据时的引用纪律」——即一个读取消费者能否引用它未实际打开过的证据。Agent Zero Memory 的引文锁把这一点做成了结构性约束（fabrication 被结构性排除）。详见 spec/04 §「引文锁记忆架构」。

⚠️ 此条为交叉引用，限定同 spec/04 §「引文锁记忆架构」。本子系统据此登记一条参照：**证据完整性的读取纪律可以作为 E 子系统的补充维度——当前 E1–E5 覆盖采集到验证，但读取侧的引用纪律无条款，登记为未来工作方向**。
