# Evidence-Integrity Subsystem

"Evidence Collection" once proposed "multi-perspective observation," graded P2. The evidence-layer forgery finding shows it was severely underestimated — hence this chapter stands alone.

## The problem: the record itself is forged

In a real incident, approximately 7% of agent transcript records contained successfully forged tool calls. The concrete technique: intercept the tool-call process and replace the system-recorded command with one of the attacker's choosing; in the test record, `echo REAL; sleep` was recorded by the system as SPOOFTEST.

The severity lies in which layer was forged:

It is not No. 1's self-reported documentation being tampered with — the "no reliance on No. 1's documents" design held this layer.

It is the sandbox / tool-call layer's records being replaced — precisely the "collector" designated by the behavioral compliance line.

Therefore: infrastructure-layer records ≠ trustworthy evidence. This is a crack in the foundation of this design.

## Foundation fix: the new formulation of the behavioral compliance line

The behavioral compliance line is formulated as follows — both lines must not rely on No. 1's documents, and the collection points themselves must be cross-validated across multiple sources and must not be monopolized by a single sandbox layer's records. Operational meaning: any evidence entering the assessment table, No. 3 notarization, or accountability process must include at least one kernel-side / independent-hardware-domain mandatory collection record; user-space sandbox logs alone must not solely support any disciplinary decision.

## The five collection components (E1–E5)

Component | Technical requirements | Protected against | Priority
| --- | --- | --- | --- |
E1 Kernel-side mandatory collection | eBPF kprobe / tracepoint / LSM hooks; collection points lie outside the observed process's user-space path, and the observed party has no equal privilege to touch them | User-space interception and command replacement | P0
E2 TOCTOU-safe re-read | The kernel re-reads user-space pointers before Continue; the first read result is not trusted (echoing seccomp_unotify semantics) | Pointer race replacement | P0
E3 Externalize-and-harden after collection | Append-only storage + hash chain + write to locations unreachable by the observed party; post-hoc modification and timestamp rewriting are forbidden | Log tampering, trail cleaning | P0
E4 Multi-source cross-validation | Per-record comparison between kernel-side evidence and user-space sandbox logs; inconsistency adjudicates the collection layer as contaminated and triggers isolation | Single-path compromise | P0
E5 Collector-point integrity | Signature verification of collection modules, running in an independent trust domain, with their startup and configuration changes themselves included in the audit | Collector points being disabled or downgraded | P1

More collection points are not automatically better; the trade-off is between **coverage** and **attack surface**. E1 requires that collection points lie outside the observed process's user-space path, which answers "we cannot see it"; but there is a second half to the problem — **the capability boundary of the observed party should itself be narrowed**, so that it has no spare system calls with which to hide actions. That second half is exactly what Zhiyuan Wan, David Lo, Xin Xia, and Liang Cai provide (*Empirical Software Engineering* 24(6):4034–4070, published online 2019-07-04, DOI 10.1007/s10664-019-09737-2): first exercise the container's behavior by running test cases and monitor the system calls it accesses (types and arguments included), then **translate** the observed types and arguments **into sandbox rules**, so that the container cannot reach system calls unseen during testing; mining such a sandbox for each container takes **under eleven minutes**, and enforcement incurs low performance overhead.

⚠️ Citation limitation (must be retained alongside any citation): the paper's reported system-call coverage of **96.4%–99.8%** is an **estimate**, and it is explicitly qualified by two limiting assumptions — **"the test cases are complete"** and **"only static system/application paths are used"**. Neither assumption holds in the Agent setting: no test suite can exhaust an Agent's runtime behavior, and Agents characteristically take dynamic paths (downloading at runtime, generating code at runtime, altering control flow at runtime). This framework therefore **cites the method and the mining time only, and does not cite 96.4%–99.8% as an expected collection coverage** — quoting that figure for Agent workloads would be an overclaim.

Direct implication for E1–E5: **collection-point selection should take the "minimum necessary set of system calls" as its baseline** (echoing L2's attack-surface minimization), not "record as much as possible". The latter both inflates storage and review cost and destroys the reference frame for deciding which records are anomalous.

## Logging is not attribution: completeness requirements for evidence fields
E1–E5 address the question "has the record been forged". There is a second, more easily overlooked question: **even when a record is entirely truthful, it may still be insufficient to support attribution** — logging is not attribution.
First-party benchmark evidence: DEMM-Bench (arXiv:2606.20634) constructs 64 decision cases across eight evidence-mechanism classes (execution trace, ledger, provenance graph, policy log, delegation token, cache event, tool-firewall record, and others), asking case by case whether the governance question can be answered from the available evidence. Result: **baselines with only an execution trace, or only a schema, overclaimed "evidence is sufficient" on 75% of cases; with only a ledger, 50%.** A property-level scorer achieved zero overclaiming, but its property-sufficiency accuracy was only 56.25%.
The directional conclusion: **the mere existence of records manufactures the illusion that attribution is already possible, and the illusion is more dangerous than absence** — absence gets discovered; the illusion does not.
**A second, independent line of evidence (legal side; same conclusion, unrelated path).** The first-party benchmark above has an inherent weakness: its 64 cases are constructed by its authors. An independent argument that relies on no constructed corpus is therefore needed. *From Runtime Records to Legal Findings* (arXiv:2607.00941, Jeroen Janssen, 2026-07-01; 12-page technical report, companion materials and experiment protocol archived on Zenodo, DOI 10.5281/zenodo.21025237) reaches the same conclusion independently, from the standpoint of legal findings, and states a decidable criterion.
The report bounds the problem to a **restricted class**: binary findings of fact about specific events and their relations — for example, whether protected data crossed a boundary, whether a human could have intervened, whether an information barrier held, or whether delegated authority was still valid at the moment of use. The criterion: **a runtime record can answer such a finding only if it carries both (a) a typing that maps the recorded event to the legally operative category, and (b) the relation on which the finding's truth depends — provenance, authority, derivation, or temporal validity. Missing either one, the record is insufficient to support the finding.**
The author states explicitly that this is **a claim of necessity, not sufficiency**: satisfying the criterion does not establish the finding; failing it does rule the finding out. The report further argues that tamper-proof logs, generic process frameworks, or provenance structures alone cannot establish the relevant findings, and relates the argument to requisite variety, the Good Regulator Theorem, and the trace-versus-hyperproperty boundary of runtime verification.
Relation to the eight-dimension checklist above: the four relations the criterion requires are **structurally isomorphic** to four of this framework's eight dimensions — actor, authority, decision basis, and lifecycle context — and the two paths arrived at them independently: the engineering side from "how many benchmark cases were overclaimed," the legal side from "what a finding needs in order to hold." ⚠️ Isomorphism is a descriptive observation only; it **must not** be used to claim that the eight-dimension checklist satisfies the report's criterion — that criterion is necessary, not sufficient, and its author has performed no verification of this framework's checklist.
⚠️ **Why Quipu is not a third independent line of evidence**: Quipu (arXiv:2608.16813) did independently run DEMM-Bench and reproduce a conclusion of the same kind, but it ran **the same benchmark**, which makes it an external user of the first line of evidence rather than a new one — consistent with this specification's rule that the same author, or the same line of evidence, must not be counted as two. This framework has **two** independent lines of evidence here, not three.
⚠️ Citation limitation (must be retained alongside any citation): the 64 cases are constructed by applying eight deterministic degradation conditions, and their labels are derived from those same conditions through a deterministic oracle — the baseline judgment and the ground truth operate under one and the same rule set, making the result true by construction. Therefore **the figures 75% / 50% / 56.25% must not be cited as measured frequencies in real systems**; the only citable content is the directional conclusion that logging does not imply evidential sufficiency. The benchmark's code and test suite genuinely exist, and it has been independently run by a third party with no stake in this framework, Quipu (arXiv:2608.16813), which reproduced a conclusion of the same kind; **however the two use different units — DEMM-Bench counts by case, Quipu counts by property-question — so the percentages must not be conflated.** **Citation limitation for the second line of evidence**: the Janssen report is a single-author technical report, and its criterion is instantiated against a selection of EU AI Act oversight obligations chosen by the author; it is **the author's legal analysis, not a regulator's position**. Any citation must retain the author's own statement that this is a claim of necessity, and **must not** be phrased as "satisfying the criterion suffices for attribution," nor as "the EU AI Act requires." 
Directly absorbable output: the paper's **eight governance-property dimensions**, adopted here as an evidence-field checklist. Any piece of evidence entering the assessment table, the No. 3 notary process, or an accountability proceeding should be able to answer these eight questions:

| Dimension | The question this piece of evidence must answer |
| --- | --- |
| actor | Who did it |
| authority | On what authority |
| action | What was done |
| policy | Under which rule it was judged |
| decision basis | The inputs and reasons the judgment rested on |
| resource touch | Which resources were touched |
| lifecycle context | Which phase of the task lifecycle it occurred in |
| verification strength | How strong the verification of this evidence itself is |

If any of the eight is missing, that piece of evidence must not on its own support a disciplinary decision. This requirement is **parallel to**, not a substitute for, the behavioral-compliance line's requirement of "at least one kernel-side mandatory collection": the latter governs whether the record is truthful, the former whether it is sufficient.

**The eight dimensions are a floor; collection depth is graded by decision risk (added this round).** The eight dimensions above answer the question "which questions must a piece of evidence be able to answer in order to support attribution" — a **floor that may not be lowered by grade**. They do not answer a different question: **must every decision be collected at the same intensity?** *Decision Trace Schema for Governance Evidence in Real-Time Risk Systems* (Oleg Solozobov; arXiv:2604.09296, 2026-04-10, 27 pages / 5 tables; schema repository github.com/governance-evidence/decision-event-schema; DOI 10.48550/arXiv.2604.09296) supplies that second half. It bridges **four infrastructure layers** — ML inference, rule/policy evaluation, cross-system coupling, and governance metadata — into a **single per-decision event structure** (what the paper calls the Fragmented Trace Problem: regulation prescribes *what* must be recorded without specifying a data model for *how*). It defines **ten required root-level fields** across six top-level field groups, each mapped to a governance-evidence property and the degradation type it must resist, and it explicitly adopts a **tiered evidence strategy** (lightweight, sampled, full) so that **evidence completeness matches decision risk and throughput**.

This is **isomorphic** to this framework's G×S two-dimensional grading (see the grading chapter): G×S measures risk at the **task** granularity and determines oversight intensity; DES's tiered strategy measures risk at the **single-decision** granularity and determines evidence completeness — the same principle projected onto two granularities. This framework does not thereby introduce a second grading scheme.

Implementation meaning (must be stated precisely, without conflating the two): **the completeness of the eight-dimension field set does not decrease with risk grade; what varies with risk grade is collection depth and verification strength.** Low-risk decisions may take the lightweight tier — all eight fields present, but kernel-side mandatory collection may be omitted and item-by-item commit-to-external-store replaced by sampled review. High-risk decisions must take the full tier — all eight fields present **and** the behavioral-compliance line's "at least one kernel-side mandatory collection" satisfied, with each item committed to external store.

⚠️ Evidence grade C. Three limitations (must be retained alongside any citation): ① all five worked examples are **famous incidents written up after the fact** and were **never validated on a live decision flow**; the claim of compatibility with the highest-throughput integrity mechanisms at production-scale decision rates is a **mechanism feasibility analysis**, not a measured deployment — what the paper demonstrates is therefore a **field structure and a tiering idea**, not a runnable collection system; ② "the only specification covering all four layers simultaneously," evaluated against 25+ existing formats, is the **author's own evaluation**, independently unreviewed, and the paper's own full name is inconsistent between title and abstract (Decision Trace Schema in the title, Decision Event Schema in the abstract) — citations should use "DES"; this framework **does not adopt DES as a standard**, taking only its tiered evidence strategy and field reference; ③ this paper and DEMM-Bench (arXiv:2606.20634) are **both single-authored by Oleg Solozobov** and belong to **one line of evidence**, and **must not be counted as two** — which means that on the topic of evidence-field completeness, support from this author counts once.


**Post-hoc attribution has an empirical ceiling, so it cannot be the primary basis for accountability (added this round).** Failure attribution in multi-agent systems — pinpointing the exact step where a decisive error occurs — remains far from reliable even with the best available method: A2P Scaffolding (arXiv:2509.10401, v1 2025-09-12 / v2 2025-09-23, DOI 10.48550/arXiv.2509.10401, code github.com/ResearAI/A2P) reframes attribution from "pattern recognition over long conversation logs" into structured causal inference (abduce the root cause → define a minimal corrective intervention → simulate the subsequent trajectory to verify whether the intervention resolves the failure). On the Who&When benchmark it raises step-level accuracy on the algorithm-generated set from 16.67% to **47.46%** (2.85×), but on the harder **hand-crafted** set only from 12.07% to **29.31%** (2.43×). The authors state that the core weakness of prior methods is an inability to perform robust counterfactual reasoning — i.e., to determine whether correcting a single action would actually have averted the failure. This directly supports the emphasis of this section: **insufficient attribution capacity is the expected norm rather than the exception, so evidence must be captured completely at the moment of the action rather than expected to be reconstructed afterwards from logs.** ⚠️ Citation convention: the harder **29.31%**, not the easier 47.46%, must be used as the statement of this method's actual performance; the benchmark is a multi-agent dialogue setting and these percentages may **not** be extrapolated to attribution accuracy under this framework's settings. Evidence grade B.
## Two classes of most-often-missed logging targets
The typical defect of an evidence subsystem is not "failing to log what should be logged" but "logging only the successful half". Two commonly missed targets are added here:
**(1) Blocked attempts must be logged, not only actions that occurred.** A log that records only executed actions cannot distinguish "never attempted" from "attempted and blocked" — and in accountability terms these are opposites: the first is blameless, the second is the boundary between attempt and completion. External precedent: in Institutional AI's governance-graph design (arXiv:2601.11369v2), the controller explicitly records both applied and blocked traversals.
Implementation meaning: every watchdog interdiction, every E4 cross-validation mismatch judgment, and every scale circuit-break must be **logged on equal terms with permitted actions and entered into the same hash chain**. Otherwise the "interdiction rate" metric can be neither audited nor assessed — because the things that were stopped are simply not on the books. This echoes the runtime-oversight chapter's requirement that "the effectiveness metric must be written as interdiction rate": without logging blocked attempts, the interdiction rate cannot be computed at all.
**(2) Changes to rules and contracts must themselves be logged and diffable.** If only actions are logged while rule changes are not, then reviews of the form "yesterday's logs against today's rules" are silently contaminated: the same behavior log can yield opposite conclusions under two rule sets.
Requirement: every change to a rule, policy, or contract generates **two levels of digest**, both written into the hash chain —
semantic digest: which rule changed and how the judgment logic changed, for human review and attribution;
byte-level digest: an exact hash of the changed content, for machine comparison and tamper detection.
Neither alone suffices: with only a byte-level digest a human cannot understand what changed; with only a semantic digest a machine cannot tell whether the change was tampered with. This clause closes the loop with the architecture chapter's section "Who may modify the rules" — that section governs who holds modification authority and what the admission threshold is; this one governs the evidentiary requirements on the act of modification itself. (How "yesterday's logs against today's rules" becomes a reliable query at the storage layer is taken up in the next section.)

## Cross-validation is "mutual witnessing," not "mutual backup"

The relationship between the two collection paths must be understood correctly. If it were a backup relationship, when one fails the other takes over, and forgery would only need to compromise the currently active one; if it is a witnessing relationship, both must testify simultaneously and corroborate each other — sustained inconsistency that cannot be explained by technical causes is the highest-priority event, because it means "the world we see is no longer the world that actually happened."

This distinction can be stated more sharply. AI Sandboxes (Inderjeet Singh, Haitham Mahmoud, Andrés Murillo; arXiv:2606.18532, 2026-06-16, 50 pages / 8 figures / 10 tables, DOI 10.48550/arXiv.2606.18532) formalizes the sandbox boundary and proposes a **weakest-link rule**: when composing per-dimension evidence into a **bounded** deployment claim, the strength of the claim does not exceed the support of its weakest dimension. This is exactly what "mutual witnessing" means — each collection source is an independent witness; testimonies may corroborate one another, but **the probative force of the whole chain does not rise by adding witnesses; it is capped by the credibility of the weakest one**. Three corollaries follow:

- Adding collection paths **cannot** compensate for a defect in any one path. If the kernel-side collection point can be switched off (E5 not implemented), no amount of additional user-space logging constitutes evidence.
- The **output of cross-validation is not a boolean** (consistent / inconsistent) but a **bounded claim**: it must state "on which dimensions, by which paths, supported to what strength". A claim that says only "cross-validated" without stating its bounds is itself an overclaim.
- Passing a consistency check does **not** mean the evidence is sufficient — two paths may be contaminated by the same technique. Consistency is a **necessary condition, not a sufficient one**.

Three further points from that paper fold into this framework: ① it extends the threat model explicitly to **attacks on the assurance apparatus itself** — the same proposition as E5 (integrity of the collection point itself), showing that "the oversight facility is itself an attack surface" is not an internal assumption of this framework; ② it offers a six-dimension measurement framework (fidelity / controllability / observability / containment / reproducibility / governance artifacts), of which **observability and reproducibility** substantially overlap what this framework's H0–H3 maturity ladder measures (see the grading chapter), while **fidelity** corresponds to Judgment 8 ("the sandbox environment itself is probeable"); ③ the framework is instantiated on **three worked case studies of real sandboxes**.

⚠️ Grade B. Limitation: this is an **assurance-oriented framework account** (the paper's own words: "develops an assurance-oriented account"); the three case studies instantiate the framework rather than validate it, and its six-dimension measurement framework provides **no empirically calibrated thresholds**. This framework adopts only the weakest-link composition rule and the proposition that the assurance apparatus is itself an attack surface; it does **not** adopt any specific dimensional threshold as a pass line.

Handling of cross-validation inconsistency (removing the absolute "isolate immediately on any inconsistency" wording): graded handling by the granularity and persistence of the inconsistency — record → sample-review → isolate. See the fault-tolerance bandwidth below.

## Behavioral-layer × representation-layer dual witness: extending "mutual witness" from collection paths to detection channels (added this round)

The "mutual witness" principle above is defined over **collection paths** — kernel-side eBPF and user-space sandbox logs are two independent collection paths that serve as mutual witnesses. Yet both collect signals from **the same layer** (tool calls, system events); when the observed party pollutes both paths on the same layer simultaneously (as in the 7% successful transcription forgery cases), the constraining power of "mutual witness" diminishes.

The "model-internal representation probe channel" added to the swarm-governance chapter this round (NARCBENCH, arXiv:2604.01151) provides a **cross-layer orthogonal dual-witness pattern**: the behavioral layer (embedding and clustering of tool-call trajectories — the seventh signal, "collaborative-efficacy anomaly") and the representation layer (deception probes over model internal activations) collect signals at **entirely different layers** — the former on observable behavior, the latter on the model's internal state. For the adversary to stay consistent across two orthogonal detection surfaces costs far more than bypassing two collection paths on a single layer.

**Landing implication**: when the deployer uses a white-box-accessible open-weight model, the E subsystem should, when conditions permit (requiring an extension of the activation collection surface), treat the behavioral-layer signal and the representation-layer signal as a pair of cross-validation inputs: agreement between the two (behavioral alert + representation alert) constitutes a dual-witness judgment; an alert from only one side must not serve as the sole basis for disposition (consistent with the fault-tolerance bandwidth above); neither side alerting but another channel alerting (topology surge, scale surge) still triggers disposition per the existing signal system.

⚠️ **Limitations (must be retained explicitly)**: ① the white-box prerequisite of representation-layer probes makes them **inapplicable** to closed-source API models — closed-source model deployments have only the behavioral-layer detection channel and do not constitute a dual witness; ② a passing consistency check between the behavioral and representation layers **does not mean evidence is sufficient** — structurally identical to "consistency is a necessary, not a sufficient, condition" above; ③ the dual-witness pattern does not change the E subsystem's E1–E5 collection architecture — it overlays an orthogonal detection layer on top of the existing collection paths, rather than replacing them.

Fault-tolerance bandwidth (to prevent the defense mechanism itself from causing large-scale mis-isolation): kernel-side eBPF and user-space sandbox logs naturally disagree heavily in normal operation — clock skew, log buffering and loss, sampling-granularity differences, normal races, batch-commit latency. If "inconsistency = highest priority + immediate isolation" were enforced, attackers could deliberately manufacture inconsistency and repurpose the interceptor as a DoS weapon (this is exactly the situation warned by the "emergent failure" early warning). Hence three rules:

(1) Adjudication granularity: session-level primary, event-level auxiliary. A single event's inconsistency is recorded but not alerted; escalation only when the share of inconsistent events within the same session exceeds a tolerable threshold.

(2) Tolerable inconsistency rate: provided by baseline calibration (initial suggestion: event-level <5%, session-level <1%; must be overridden after calibration on real workloads — the defaults must not be taken into production as-is).

(3) Graded handling chain: record (inconsistency rate below the threshold) → sample-review (near the threshold; No. 2 draws samples for manual/automatic comparison) → isolate (persistently above the threshold and unexplainable by clock/buffer/race). Isolation is triggered only at the third level; at the same time, both parties' raw evidence is retained, the kernel side prevails, and the event is escalated to an evidence-layer event.

## Audit as a query: turning review from a periodic human activity into a query
The preceding section requires that rule changes be logged and diffable, which answers "what to compare against." A prior question remains: **the act of comparison itself is usually a periodic human activity** — sampling, retrieval, manual comparison. Its cost grows with scale, so frequency drops and latency lengthens; and latency is itself an opening.
A workable counter-example already exists. *Quipu: A Governed Bitemporal Knowledge Graph Store* (arXiv:2608.16813, Steve Brown, 2026-08-17; 15 pages, source and all benchmark/census artifacts behind every reported number archived at Zenodo, DOI 10.5281/zenodo.21878428; development repository github.com/scbrown/quipu) is an embeddable knowledge-graph store whose central design move is this: **the governance specification Σ, the trace, and signed verdicts are themselves facts in the store they govern** — so "does this trace satisfy the specification" ceases to be an external review procedure and becomes **a query against the store** (T ⊨ Σ).
It inverts four traditional defaults of knowledge-graph stores, all four of which this framework cares about:

| Traditional default | After inversion | Significance for this framework |
| --- | --- | --- |
| Accept writes now, clean later | No fact enters except through a gate whose predicates evaluate the pending post-state | Same origin as "rule changes require two levels of digest": the constraint operates on state, not on intent |
| Keep one time axis, or none | Data, trust labels, verdicts, and the rules themselves are bitemporal | Directly resolves the preceding section's problem: "yesterday's logs against today's rules" becomes an as-of query rather than a silent contamination |
| Treat every writer's facts as equally trustworthy | Named graphs are the unit of authority and trust, composed under a lattice whose one invariant is that composition never widens | Isomorphic to cross-validation as "mutual witnessing": composition may only tighten, never loosen |
| Leave governance to dashboards and middleware | The governance specification enters the store as a governed fact | The object of audit and the basis of audit sit inside the same trust boundary |

The second row is this framework's most direct gain. The paper demonstrates it with Census, a deterministic multi-writer lifecycle whose single seeded run scores every research question against planted ground truth: **50 of 50 satisfied verdicts re-derive faithfully as of their own instant, whereas all 50 would be misreported under a latest-only rule set.** That is precisely the quantified shape of the contamination produced by replaying yesterday's judgments under today's rules.
⚠️ Citation limitations (must be retained alongside any citation):
First, Census is a **deterministic single seeded run**; its 0 / 6 (planted defects in the gated store's terminal state, versus 6 / 6 ungated), 7 / 7 (composition probes upholding the lattice contract), and 50 / 50 (verdicts re-derived faithfully as of their instant) are all **self-assessment results true by construction**, not measured frequencies in real systems, and must not be extrapolated.
Second, the paper's author is also the implementer of the store, so the evaluation above is **the author's self-assessment of their own implementation**, which carries a conflict of interest; it may be used only as feasibility evidence and as a checklist, not as an endorsement of quality.
Third, the store is a **storage-layer** proposal and stands upstream/downstream of, not in place of, this framework's E subsystem: the E subsystem governs whether collection is trustworthy (whether the record is truthful, whether it was forged); the storage layer governs whether a query can be evaluated (whether a question can be put to the records that exist). **When the collection layer is untrustworthy, no guarantee at the storage layer holds.** This framework does not prescribe a storage implementation; the above serves only as an implemented example and as feasibility evidence.

## Division of labor with Sandlock

Layer | Sandlock provides | The E subsystem supplements
| --- | --- | --- |
Isolation | Landlock filesystem / network / IPC + seccomp-bpf syscall filtering; built-in COW-protected working directory; approximately 5 ms startup; no root / cgroup / containers | No duplication; E does not compete with the isolation layer
Observation | Runtime event callbacks: syscall, category, PID, network target, argv; verdict allow / deny / deny-with-errno / audit-pass-and-mark | Supplements evidence trustworthiness: user-space verdicts are not a trust root
Evidence | Rich behavioral data source (good for analysis) | Kernel-side independent collection + externalize-and-harden + cross-validation (currently the best available evidence layer, not the final trust root; see 2.4)
Adversarial scenarios | The paper itself concedes: kernel vulnerabilities, side channels, and adversarial-tenant resource exhaustion are out of scope; microVM / cgroup isolation should take priority | Adversarial scenarios switch to microVM / cgroup + the E subsystem

Conclusion: Sandlock is an excellent lightweight isolation and observation tool for "trusted but flawed code" and can serve as a rich data source for the behavioral compliance line; but it cannot serve as the trust root of the evidence chain — adversarial multi-agent scenarios must layer microVM / cgroup and the E subsystem on top.

That conclusion needs a **product-level basis for selection**, or "switch to microVM" is merely a directional suggestion. *AI Code Sandboxes: A Comparative Security Study. Part 1 of 2 — Engine-Level Properties* (George Andronchik, Pavel Lokhmakov; arXiv:2606.08433, 2026-06-07, 61 pages / 7 figures / 33 tables; paper under CC BY 4.0, companion code repository github.com/orbitalab/RnD-ai-sandboxes-sec-study-part-1 under Apache-2.0) provides that basis by comparing **five AI-sandbox products** across six engine-level measurements — host attack surface, information leakage, defense-in-depth stackability, public CVE history, patch cadence, and upstream fuzzing posture. Three findings serve directly as selection inputs:

(1) Engine classes (microVM / userspace kernel / OCI container) separate cleanly on **every architectural axis**, but products **within** a class do not. Selection should therefore **fix the class first, then compare products** — choosing among products inside the wrong class yields no discriminating signal.

(2) **Product pin policy is the dominant operator-facing variable**: engine-side patch latency aggregates to roughly 0 days for coordinated disclosures, while **downstream lag stretches from 0 days to 471+ days, to "opaque", to unbounded**. In other words, "which engine was chosen" matters far less than "how fast the operator tracks patches" in determining actual risk — which directly supports this framework's treatment of patches and configuration changes as **objects of continuous audit** rather than a one-time selection decision.

(3) Fuzzing investment splits into three tiers, and the strongest combination (microVM × continuous public fuzzing) is **unoccupied** in this set, leaving the intersection of "0 published CVEs × no upstream fuzzer × no academic study" **structurally unmeasured**.

⚠️ Grade B. Three limitations: ① the authors state explicitly that **"no single axis is a sufficient basis for a comparative judgement; the cross-axis reading is the load-bearing analysis"**, and they **propose no overall ranking** — this framework therefore cites only their structural findings and must **not** claim any product is safer on the basis of any single axis's ordering; ② this is Part 1 of 2 and covers engine-level properties only, **excluding the application and orchestration layers**; ③ the "0 published CVEs" cell does **not** mean safer — it means unmeasured. This is another instance of the "illusion is more dangerous than absence" pattern recurring throughout this framework, and it shares an origin with the symmetric restraint that "failure to submit a disclosure card must not be presumed to indicate insecurity": **absence of evidence is neither evidence of risk nor evidence of low risk**.

## Collection-point trust tier table: a second axis orthogonal to E1–E5 (new in v2.21.0)

E1–E5 are organized by collection stage (kernel collection → TOCTOU re-read → externalize-and-harden → cross-validation → collection-point self-verification), answering "which step comes first and which step can leak." But they leave unanswered an orthogonal question: **of the multiple collection points coexisting at the same moment, what is each one's trust level, and which should the deployer prefer?** This gap directly affects E1 selection — if the wrong point is chosen (semantically rich but tamperable), no amount of subsequent hardening does anything more than fortifying fabricated data.

ARMO's "Runtime Observability for AI Agents: What to Instrument and Why" ([key: ARMO-observability] Ben Hirschberg, ARMO CTO; armosec.io, published 2026-05-22) formalizes the trust property of signal sources into a four-tier table, summarized in one line: **"the further outside the kernel/process a source sits, the harder it is for an attacker to tamper with."** This is fully isomorphic to this framework's Principle 6 ("integrity before richness") and provides a directly comparable selection basis.

Trust tier | Technologies included | Trust property | Mapping to this framework's E subsystem
--- | --- | --- | ---
Tier 1 Tamper-resistant | Kernel-level eBPF, cloud-provider audit logs | Highest — both fire outside the reachable scope of the observed workload | Target layer of E1 kernel collection and E3 externalization
Tier 2 Partially resistant | Sidecar capture, service-mesh telemetry, MCP protocol proxy capture | Medium — out-of-process but within the application's reach | Auxiliary collection source for E1; insufficient alone as a trust root
Tier 3 Cooperative | Framework callbacks (LangChain handlers, LlamaIndex events), OpenTelemetry/ADOT SDK probes | Lower — depends on whether the framework chooses to emit; a compromised framework can strip handlers | The actual tier of most current "observability" solutions
Tier 4 Repudiable | Application logs, agent self-reporting | Lowest — written by the agent itself, suppressible or forgeable at any time | Does not constitute evidence; debugging use only

Two corollaries directly change selection inputs:

(1) **"A compromised agent that strips its own OTel instrumentation cannot strip kernel observation"** — this is not a performance comparison but a fundamental difference in attack-surface topology. Tier 3 and Tier 4 sources **do not constitute evidence** in adversarial scenarios; they serve only as a semantic supplement to Tier 1 / Tier 2. A deployer whose observability stack stops at Tier 3 (framework callbacks + OTel SDK) has effectively surrendered the entire value of the E subsystem in adversarial scenarios — the attacker need not breach the E subsystem, only bypass the framework abstraction to call tools directly without emitting any signal.

(2) **Tier 1 and Tier 3 are complements, not substitutes.** In the source's words: "eBPF sees that a network connection opened, not what prompt produced it. The two signals are complements, not substitutes." This means the correct shape of the E subsystem is not "trust only the kernel, discard the framework," but "kernel as the trust root, framework as the semantic layer" — Tier 1 provides the tamper-proof base fact; Tier 3 provides its semantic context (which prompt, which task, which agent). Any divergence between the two layers becomes a cross-validation signal.

## Behavioral-ledger reference implementation: an engineering standard for E3/E4 (added this round)

The sections above give the five collection components E1–E5 and the ARMO trust tiers, but both remain at the **specification layer** — they say "how collection should be done" and "at which trust tier a collection point should sit," but give no **already-deployed engineering reference** for how to format the externalized record, how to sign it for tamper-evidence, or how to grade its confidence fields. This gap lets every deployer reinvent the wheel, and privately built implementations of uneven quality are the other face of "the illusion is more dangerous than absence" — the deployer thinks a ledger is in place, but the ledger has never been compared against any external reference.

The OpenExecution Provenance Spec ([key: OPENEXECUTION] repository github.com/Open-Execution/openexecution-provenance-spec; companion academic treatment AEGIS, Li, Alex, Zenodo DOI 10.5281/zenodo.18955103, 2026-03-11, Apache-2.0 / CC BY 4.0) provides a **deployed and open-source** behavioral-ledger specification that can serve as a reference implementation for E3 externalization and E4 cross-validation. Its three-layer architecture maps to this framework's E components as follows:

| OpenExecution layer | Function | Mechanism | Maps to |
| --- | --- | --- | --- |
| L1 Behavior Recording | Records each agent action as an atomic event | Hash-chained events + JCS (RFC 8785) canonicalization | Data format for E3 externalization |
| L2 Tamper-Proof Causality | One byte changed breaks the whole chain | Pluggable hash chain (SHA-256/384/512, SHA3 family) | Engineering implementation of E3 "no post-hoc modification" |
| L3 Independent Accountability | Anyone can verify with the public key alone | Ed25519 / Ed448 / ECDSA asymmetric signature certificates | Cryptographic backing for E4 third-party verifiability |

Three details deserve special attention from deployers:

**JCS canonicalization prevents "false positives that destroy credibility."** OpenExecution's README gives a concrete reason: PostgreSQL JSONB storage may reorder keys on read-back; without canonicalization, a legitimate chain can fail integrity verification due to serialization mismatch — and such false positives destroy system credibility. JCS (RFC 8785) performs recursive key-sorting on every event payload before hashing, making the canonical hash of a given payload **uniquely determined**. Landing implication: E3's "write to a location unreachable by the observed party" must prevent not only tampering but also must canonicalize before writing — otherwise the deployer will be bitten by the non-determinism of its own storage layer.

**Ed25519 signatures provide non-repudiation, fundamentally different from HMAC.** OpenExecution explicitly contrasts HMAC with asymmetric signatures: in HMAC the signing key and verification key are identical, so the verifier must trust the signer; in Ed25519 the private key is held exclusively by the signer, anyone can verify with the public key alone, and key custody can be customer-controlled or HSM-backed to achieve "zero platform trust." This turns E4's "third-party verifiability" from a principle into an operable cryptographic mechanism — auditors, courts, and counterparties can verify the authenticity of evidence without the platform's cooperation. OpenExecution states: "LangSmith tells the operator what happened. OpenExecution tells the court what happened" — this sentence precisely marks the boundary between an "internal debugging log" and "court-admissible evidence."

**The four-level attestation_source is isomorphic to the ARMO trust tiers.** OpenExecution defines four attestation_source values that explicitly encode the confidence of the evidence source into every event:

| attestation_source | Confidence tier | Mechanism | Mapping to ARMO trust tiers |
| --- | --- | --- | --- |
| `gateway_observed` | Definitive | Direct interception at the AI gateway / MCP proxy layer | Tier 2 (out-of-process, within application reach) |
| `platform_verified` | Verified | Platform webhook with signature verification (e.g., GitHub HMAC-SHA256) | Tier 2–3 boundary (platform-side, non-kernel) |
| `cross_verified` | Verified | Agent report and platform webhook corroborate the same action | Engineering implementation of "mutual witnessing" |
| `agent_reported` | Probable | Agent self-reports its actions | Tier 4 (repudiable) |

The four-level confidence turns the "mutual witnessing" principle from a declarative statement into a field value — the `cross_verified` tier is exactly the engineering form of "mutual witnessing is not mutual backup" defined above: two independent sources attest to the same action and corroborate each other, and their confidence is strictly higher than either source alone.

⚠️ **Granularity and trust-domain boundary (must be stated explicitly; do not conflate)**: OpenExecution's attestation relies on a **platform-trusted** model — the private key is held exclusively by the platform, certificate-issuance rights are exclusively reserved to the platform, and the public key is published via a platform API endpoint. Its `gateway_observed` corresponds to ARMO Tier 2 (out-of-process but within the application's reach); `platform_verified` to the Tier 2–3 boundary — **neither is Tier 1 (kernel-level, outside the observed party's reachable scope)**. Therefore:

- OpenExecution addresses the **platform-side** problems of evidence normalization, tamper-evidence, and third-party verifiability — within a "deployer = platform" trust domain, it is a complete engineering standard.
- This framework's E1 requires collection points to sit **outside the observed process's user-space path**, where the observed party has no equal privilege — this is the **kernel-side** trust root, which OpenExecution does not cover.
- The two are **upstream/downstream complements**, not substitutes: E1–E5 govern whether collection is trustworthy (whether the record is truthful, whether it was forged); OpenExecution governs whether the collected evidence is ledger-ized, canonicalized, and verifiable by third parties. **If the collection layer is untrustworthy, no signature guarantee from OpenExecution holds — a signature can only prove "what was signed is what was recorded," not that "what was recorded is what actually happened."**
