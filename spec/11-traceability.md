**溯源关系本身也须可核验（本轮新增）。** Ayush Aggarwal、Mohammad Arif Baig，*Enhancing DevSecOps Practices for Secure AI Platforms Using SABSA*（IEEE Internet of Things Journal，**Early Access**，2026-07-29 发表，DOI 10.1109/JIOT.2026.3717946）把 SABSA 安全架构框架与 DevSecOps 工程流水线一并落地，弥合「抽象风险治理」与「技术实施」之间的鸿沟，并以 IaC（Checkov）扫描实现**多层架构的可追溯性**。该做法提示一个本体系尚未覆盖的面：**溯源关系可以是流水线的自动产物，而不必是人工编制的文档**。本表（机制溯源表）当前是人工编制、人工维护的——「机制 → 依据」各行与正文实际内容的同步并无自动校验；门禁已自动校验 REFERENCES 与 spec/ 之间的引用键一致性，但本表不在其内。该缺口登记为 **未解问题 #28**。⚠️ 四项限定（Early Access 未定稿分页；实验对象为 DistilGPT-2 微型模型 + **模拟**对抗向量，存在实质域迁移缺口；只覆盖**直接**提示注入、不含间接；摘要只称 "robust absolute mitigation rate"、未给出缓解率数值）使本条仅为**概念采纳**：只采纳「可追溯性可由流水线自动产出」这一概念，其 41.6 ms 开销上界与任何缓解率数值**均不引用**。

## 结构迁移声明：从扁平「机制 → 依据」向 CAE 三层框架（v2.22.0 新增）

本表当前是「**机制 → 教训/来源 → 等级 → 依据**」的扁平结构。安全案例方法论给出了一个更可审阅的替代——**CAE 三层结构**（主张—论证—证据）。三条路径无关的独立来源共同支撑这一升级：

- 【键: safety-cases-justification】（arXiv:2403.10462，Clymer / Gabrieli / Krueger / Larsen，2024-03）：提出「safety case」——一份由「主张—论证—证据」三层组成的结构化论证，论证系统在给定运行上下文中不太可能引发灾难。给出四大类论证骨架（完全无能 / 充分控制 / 尽管有能力仍可信 / 对可信 AI 顾问的遵从）。
- 【键: safety-cases-frontier-ai】（Governance.ai，Buhl / Sett / Koessler / Schuett / Anderljung，2024-10-28）：把安全案例方法论落到前沿 AI 治理，论证其在行业自律与政府监管中的适用性，并讨论产出一份前沿 AI 安全案例的实操步骤。
- 【键: assurance-framework-aies】（arXiv:2504.16937，Kapusta 等 7 位，MITRE / DOD CDAO / JHU APL，2025-04，已发表于 SPIE D+C 2025）：提出基于主张（claims-based）的 AI 系统保障框架，覆盖 AI 系统全生命周期——与安全案例互补：安全案例聚焦「会不会引发灾难」，保障框架覆盖「从开发到退役是否持续满足使命目标」。

**升级分两步走**（映射表已建议）：**第一步**（v2.22.0）重构本节章节结构为 CAE 三层框架——声明结构、登记方法论来源、在下表表头标注「迁移目标列」；**不补全**所有 49 行的论证链。**第二步**（v2.23.0，本版）已逐行补全论证链——把每一行的「教训/来源」拆为「**主张**：该机制解决了什么问题 → **论证**：为什么该来源支撑该主张 → **证据**：该来源的可核验引用键」，并扩展门禁脚本（新增第 36 项）静态校验每行必须同时含三个 CAE 标记词。⚠️ 三项保留限定：① 本体系升级为 CAE 后**不替代正式的安全案例认证**——它只是机制级溯源的可审阅结构；② CAE 结构形式化不等价于论证本身的正确性——组合错误的论证仍可被 CAE 形式化但内容无效，需独立审查；③ 论证链的补全工作量与本表行数（49 行；v2.24.0–v2.26.0 各新增一行，现为 52 行）成正比。
