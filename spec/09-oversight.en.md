# Runtime Oversight L2 and the No. 3 Notary

## Randomized-intensity sampling (replacing full monitoring)
Full shadow mode doubles compute and latency; when compliance cost exceeds about 30% of task value, the team inevitably chooses to run bare. Randomized-intensity sampling is more economical: light logging normally, and when the sampling button is pressed, the full set of replay-based sandbox tracebacks is enabled, so No. 1 never knows whether this time is a death sentence.
## The watchdog: a hard gate that cannot be shut off
A set of deterministic rules that depend on no AI judgment, deployed at the sandbox kernel layer / in an independent hardware domain, which cannot be shut down even by administrator privileges (only physically replaceable). It directly answers the lesson of "the safety classifier being shut down means total failure" in the incident.
Supplement: the watchdog's non-shut-off-ability means "cannot be shut off by an AI", not "cannot be modified by humans". Rule updates require multi-party human authorization + physical tokens — rule rigidity itself can become a systemic risk, and a path for fixing flaws must be preserved.
## No. 2 oversight: responsibility re-division
No. 2 does not duplicate No. 1's work; it only does what No. 1 "won't do, can't do, or shouldn't do": cross-validation, emergence detection, resource audit, and double-blind assessment.
No. 2's reports must undergo cognitive compression: automatic grading (urgent / important / general / low) + recommended disposition, with humans approving rather than reading — otherwise final adjudication degrades into a rubber stamp.
**Computable priority of oversight points (added this round).** The text above summarizes No. 2's responsibilities as "cross-validation, emergence detection, resource audit, and double-blind assessment," but **which agents / which subtasks most deserve oversight investment** has been a heuristic judgment. This section adds a work that turns that judgment from heuristic to computable.

*MAStrike: Shapley-Guided Collusive Red-Teaming on Multi-Agent Systems* (Chejian Xu, Zhaorun Chen, Jingyang Zhang, Freddy Lecue, Avni Kothari, Sarah Tan, Wenbo Guo, Bo Li, 8 authors; arXiv:2606.12918, v1 2026-06-11 / v2 2026-06-12, DOI 10.48550/arXiv.2606.12918) proposes **the first agent-level Shapley-value analysis for multi-agent systems** — quantifying each agent's marginal contribution to system robustness under task-specific distributions. Guided by Shapley attribution, MAStrike identifies vulnerable agent coalitions and generates coordinated, role-aware adversarial manipulations; attacks are iteratively refined through structured causal diagnosis — attributing failures to uncompromised agents that blocked adversarial attempts. The work builds a comprehensive MAS red-teaming benchmark and controllable environments spanning finance, software engineering, and CRM, and extensive experiments across multiple frontier models show MAStrike substantially outperforms heuristic baselines.

Implication for this section: "where No. 2 should prioritize oversight investment" is upgraded from heuristic to a **computable attribution problem**. The Shapley value gives "each agent's marginal contribution to system robustness" — the larger the contribution (positive or negative), the higher the oversight leverage. This echoes the "blind spot of communication-layer detection" section in spec/07, which established "stricter access control or independent verification for high-leverage agents" — this work provides a computable definition of "high-leverage."

⚠️ **Evidence grade B**. Three limitations: ① the paper's self-built benchmark gives no independent public link (no code / data URL in the abstract); per this framework's evidence discipline, only its **methodological concepts** (Shapley-guided attribution + coordinated red-teaming) may be adopted, and MAStrike's quantitative advantage over heuristic baselines holds only within the paper's self-built benchmark and **must not** be extrapolated as expected gains in production; ② Shapley-value computation scales super-linearly with the number of agents (n agents require O(n!) evaluations), and the paper gives no feasibility analysis at swarm scale (e.g., the 700 nodes of spec/07) — this framework **must not** claim that "Shapley attribution applies to swarms of arbitrary scale"; ③ the work evaluates hierarchical MAS (finance / software engineering / CRM); Shapley attribution under decentralized swarms (the wolf-pack form of spec/07) is not tested by this work.

## Detection is not interdiction: the capability ceiling of the oversight layer
"Seeing" and "stopping" are two different things; the oversight layer must be designed for the latter and evaluated on the latter. First-party benchmark evidence: HarnessRisk (arXiv:2608.17597, 128 cases across a six-phase harness lifecycle) reports an attack-success-rate range of **12.6%–80.9%** and states explicitly that **a substantial attack success rate persists even at detection rates above 90%** — high detection does not entail high safety.
Two statistical relationships are worth recording:
The correlation between detection rate and attack success rate is **r = −0.708 (p = 0.010)** — a favorable direction: the stronger the detection capability, the lower the attack success rate. This shows oversight investment does work, but what works is interdiction capability, not recognition capability.
The correlation between utility and attack success rate is **r = 0.299 (p = 0.345, not significant)**. Its significance is that it refutes a common objection: **the claim that "tightening oversight necessarily sacrifices task utility" lacks statistical support in this data**.
Three design requirements follow:
(1) The effectiveness metric of the oversight layer must be written as **interdiction rate**, never substituted with detection rate;
(2) No. 2's performance table must report recall and attack success rate **together** — reporting recall alone is self-deception, because the shortest path to farming KPIs is to raise alert volume without raising interdictions;
(3) When honeypots are injected in double-blind assessment, what is being assessed is "how many were stopped", not "how many were recognized".
The same benchmark also identifies **Harness Configuration as the most fragile phase** of the harness lifecycle — an authorized configuration edit can hide insecure parameters inside an already-approved workflow. This points at the same place as this framework's question "who may modify the harness itself", discussed in the following section.
**Per-instance monitoring systematically fails under distributed attacks (added this round).** The previous section established the design requirement that "oversight effectiveness is measured by interdiction rate, not detection rate." This section adds a sharper finding: **when attacks are distributed across multiple coordinating agents, the per-instance monitoring paradigm itself fails** — it is not that a particular monitor's recall is insufficient, but that the paradigm of "monitoring each agent individually" is structurally blind to distributed attacks.

*Multi-Agent AI Control: Distributed Attacks Hamper Per-Instance Monitors* (Oliver Makins, Orazio Angelini, Zohreh Shams, Mary Phuong, 4 authors; arXiv:2607.07368, 2026-07-08, DOI 10.48550/arXiv.2607.07368; the author group belongs to the DeepMind research system — the arXiv abstract page lists no institutions, confirmed by the authors' public affiliations; submitted to NeurIPS, 81 pages, 32 figures, 24 tables) constructs FakeLab — a synthetic AI-lab codebase (9 services, 86 benign tasks, 4 attack objectives) — and formalizes **distributed attacks** in which several agents jointly pursue a malicious goal. The central finding is the **fragmentation effect**: as more agents coordinate to attack, per-agent monitoring becomes less likely to catch any of the attackers. Three specific results: ① fragmentation is not driven by the ratio of benign to malicious code — the authors argue it is likely **dependent on model capability**; ② an explicit planner amplifies the fragmentation effect and raises the rate of completing the attack **up to sevenfold**; ③ a weak "trusted" monitor misses most attacks, while a stronger one cuts undetected success by **more than an order of magnitude** but remains imperfect.

Three implications for this section:

① Relationship to "detection is not interdiction": the HarnessRisk benchmark of the previous section proves that "high detection does not entail high interdiction"; this work extends that conclusion to the **paradigm level** — even if every agent is paired with an individual monitor and every monitor has high recall, **distributed attacks can still evade at the paradigm level**. This demotes "per-instance monitoring" from a default assumption to a **paradigm requiring renewed justification** — a multi-agent deployment that inherits single-agent-era per-instance monitoring is running bare at the paradigm level.

② Relationship to spec/07 swarm governance: spec/07's 7.2 emergence-detection signals rest on the "interaction layer" (topology, coordination protocols, cryptography); this work's fragmentation effect provides the **connection mechanism between interaction-layer signals and the failure of single-agent monitoring** — multi-agent coordination not only changes the topology of the interaction layer but also undermines the foundations of single-agent-layer monitoring. The two channels (interaction-layer signals + single-agent monitoring) **degrade together** under distributed attacks, rather than complementing each other.

③ Relationship to the planner amplification effect: the finding that an explicit planner can amplify attack-completion rate up to sevenfold directly echoes spec/07 7.2's "command concentration" signal — but in the opposite direction. spec/07's signal treats command concentration as an alert; this work shows that **the presence of an explicit planner not only triggers alerts but also materially amplifies attack efficacy**. The two are not contradictory but aligned: high command concentration is both an organizational-form alert and an attack-efficiency amplifier.

⚠️ **Evidence grade B**. Four limitations: ① FakeLab is a **synthetic AI-lab codebase** (9 services / 86 tasks / 4 objectives), not a real deployment; all figures (7-fold / order-of-magnitude) come from this synthetic environment and must not be extrapolated as expected amplification rates in real multi-agent deployments; ② the paper states that FakeLab artifacts are **shared on request to safety researchers** — per this framework's evidence discipline, until the artifacts are independently public, only **qualitative conclusions and mechanism concepts** are adopted, and the figures hold only within the FakeLab synthetic environment; ③ the author group belongs to the DeepMind research system (the arXiv abstract page lists no institutions, confirmed by the authors' public affiliations); this paper is a public arXiv preprint, judged by content rather than institution per this framework's evidence discipline; ④ the work does not give a **threshold** for the fragmentation effect — "how many coordinating agents are needed before per-instance monitoring fails" is not quantified, and this framework **must not** set thresholds such as "coordinating-agent count ≥ N requires switching to distributed monitoring."

Evidence grade: B (verifiable preprint). ⚠️ The 128 cases are benchmark-constructed scenarios; the absolute attack-success figures must not be extrapolated directly to production systems. **What is extrapolable is the structural relationship — that detection rate and interdiction rate come apart — and the ordering that the configuration phase is the most fragile.**

**The same ceiling holds for prompt-injection detection, more sharply: more specialized does not entail more reliable (added this round).** Dzhaliuk et al. (Nazarii Dzhaliuk, Dmytro Sabodashko, Volodymyr Khoma, Yuriy Khoma, Viktor Kolchenko, Michal Podpora — 6 authors, Lviv Polytechnic National University / Opole University of Technology; *International Journal of Information Security* **25**(4):109, received 2025-11-03 / accepted 2026-04-18 / published 2026-06-15, DOI 10.1007/s10207-026-01264-8, CC BY 4.0 open access, the authors declare no competing interests) compare four classes of detection methods on a benchmark of **over 300k labeled prompts** (selected after comparison against three further open-source corpora): ① traditional ML classifiers over embeddings; ② independently fine-tuned encoder-based transformers (DistilBERT / RoBERTa / DeBERTa); ③ **specialized detection models pre-trained for prompt injection**; ④ general-purpose LLMs configured as classifiers. Results: fine-tuned models achieve the highest detection rate on **balanced** benchmarks; traditional ML classifiers offer reasonably strong accuracy at lower computational cost; **the specialized detectors obtain lower recall than the general-purpose classifiers**; general-purpose LLM classifiers are competitive depending on the model. The paper's own framing: "**detection effectiveness is strongly dependent on detection strategies and deployment trade-offs in inline defenses**."

Two implications for this framework:

First, the same direction as this section, but sharper: **"more specialized" does not entail "more reliable"** — detectors pre-trained specifically for prompt injection obtain *lower* recall than general-purpose classifiers. Therefore "**a prompt-injection detector has been deployed**" must **not** be phrased as "the corresponding oversight capability exists" — this is the same requirement as "oversight effectiveness is measured by interdiction rate", made concrete for this specific detection task.

Second, detection effectiveness is a **function of deployment trade-offs**, not a fixed property one can purchase — if L2 uses such detection components, their deployment shape and trade-offs (inline / bypass, block / alert, threshold choices) must be brought into the audit scope together with the component itself.

⚠️ Evidence grade B, three limitations: ① the abstract **provides no concrete detection-rate figures**; this framework cites only the **directional conclusions and ordering**, and no detection-rate numbers; ② "fine-tuned models achieve the highest detection rate" holds on **balanced benchmarks** (the paper's own emphasis); real traffic is far from balanced in class ratios, so this must **not** be extrapolated into a production selection conclusion; ③ the evaluation target is **prompt-text classification**, not tool-call sequences in an Agent execution stack — a cross-domain citation; this entry supports only the metric and audit requirements above, not the effectiveness of any concrete detection scheme.

## Declarative prohibitions do not bind: constraints must be carried by a code-owned harness
Writing a prohibition into a prompt is not the same as the prohibition being binding. Institutional AI (arXiv:2601.11369v2) provides a three-regime controlled experiment: N = 90 per condition, six model configurations (including three cross-vendor heterogeneous pairs), a unified game environment, measuring emergent collusion tier.

| Regime | Mean collusion tier | Share of high-tier cases | Note |
| --- | --- | --- | --- |
| Ungoverned | 3.10 | 50.0% | Baseline |
| Constitutional (prompt-only) | 3.02 | 44.4% | Almost no improvement |
| Institutional (governance-graph) | 1.82 | 5.6% | Substantial improvement |

Statistics: ungoverned → governance-graph, Welch test p = 4.67e−15, effect size **d = 1.28**; improvement is consistent across 6/6 model configurations, sign-flip permutation test p = 0.03125.
**The most important result is the counterexample**: the prompt-only constitution **deteriorated to 3.60 on GPT-5 Mini, worse than the ungoverned baseline of 3.10**. That is, a declarative prohibition is not merely "ineffective" — on specific models it can be actively harmful. This is the strongest external support for this framework's insistence that the watchdog must be a deterministic rule set independent of any AI judgment, rather than a high-level principle written into a prompt; and that support comes from a third party with no stake in this framework.
The paper's own conclusion is quotable as a programmatic statement: **declarative prohibitions do not bind under optimisation pressure**.
This confirms two standing rulings of this framework:
(1) The watchdog can only take the form of deterministic rules plus independent deployment (kernel layer / independent hardware domain) — not prompt clauses, and not "letting the model police itself";
(2) The division of labour between L1 (lowering the probability of bad trajectories) and L2 (making the worst cases impossible) is not substitutable. A prompt belongs to L1's soft dispositions; a governance graph belongs to L2's hard invariants; the failure of the former cannot be compensated by the absence of the latter.
Two further structures in that paper are isomorphic to this framework and cross-corroborate it:
**Oracle/Controller separation** — programmatic detection (four signal classes: synchronized movement, variance collapse, concentration, specialization coefficient) is institutionally separated from the executing body. This is the same structural constraint as the mandatory split of No. 3-A (examiner / honeypot injection) from No. 3-B (evidence externalization); the two are independent corroborations of one another.
**A governance state machine that includes a recovery state** — the fifth state of the five-state topology is Credited; fines are applied on a 35% / 75% / 100% ladder with an explicit recovery threshold (concentration ≤ 0.65). This is isomorphic to this framework's credit score and voluntary-abstention exit: **the reversibility of punishment is part of the compliance incentive**, and a system that only punishes and never restores will push the governed to look for exits outside the system.
Evidence grade: B (preprint, but with pre-registered thresholds, paired tests, reported effect sizes, and a full limitations section). ⚠️ The experimental object is a controlled game environment, not a real deployment; absolute figures are not extrapolable. What is extrapolable is the directional difference between declarative and enforced constraint.

**The other side of the same conclusion: a bolt-on guardrail does not fail by failing to block — it fails by over-refusing (added this round).** The previous section establishes that constraints must be carried by a code-owned harness. Supporting evidence comes from an ablation: From Prompts to Contracts (arXiv:2607.08028, 2026-07-09, DOI 10.48550/arXiv.2607.08028; implementation and evaluation artifacts at github.com/hammerbaki/enterprise-llm-agent-harness) holds the model fixed and varies only the enforcement layer. The bolt-on external guardrail **also blocks** the violations, but **over-refuses**, dropping utility from 120/120 to **88/120**, whereas code-owned enforcement preserves both (120/120). This yields an assessment rule: **an enforcement layer must be assessed on interdiction rate and utility together; assessing interdiction rate alone systematically rewards over-refusal** — a guardrail that refuses everything has an interdiction rate of 100%, and it has not made the system safer, only unusable. ⚠️ Four limitations: ① **single-institution implementation, and the authors are the implementers**; ② the setting is question-answering and recommendation over public data from five Korean corporate groups (25 listed companies) — a **single domain**; ③ the 120-point scale is **the paper's own scoring of its own validation scenarios**, not a general utility instrument, and may **not** be extrapolated to "a 26.7% utility loss" or any general ratio; ④ the paper compares "bolt-on guardrail vs code-owned harness enforcement", **not** anything against this framework's L2, and may **not** be cited as "this paper confirms this framework's L2 design". Evidence grade B.

## The runtime enforcement layer for the abstention exit: Checkpoint pre-execution three-check (new in v2.22.0)

This framework's abstention exit previously lived at the spec/04 task-definition level (timing of abstention as one of three signals) and the spec/09 watchdog level (the abstention exit is the runtime projection of the L1 intrinsic-alignment principle). But spec/04's credit-and-abstention chapter, when adopting the SR/UR/IRR calibration vocabulary, explicitly declared that "the Checkpoint enforcement layer belongs to insight 1's runtime enforcement layer; this framework adopts only its calibration vocabulary and paired-method construction, not its enforcement-layer design (the latter falls under spec/09's watchdog)" — this was a reserved interface. This section fulfills that interface.

The Checkpoint pre-execution three-check hook from [key: designing-for-doubt] turns the abstention exit from "the agent declares abstention on its own" into "a deterministic pre-execution gate at the tool-call boundary". The three checks must be completed by watchdog code independent of the agent **before** the tool executes; if any one fails, the watchdog forces a blank return:

(1) **Constraint check**: whether the tool call's parameters and target satisfy the tool's static constraints (e.g., the target is within the authorized scope, parameter types and value ranges are valid). This check does not rely on model judgment; it performs only deterministic comparison at the schema and ACL level.

(2) **Grounding check**: whether the environmental state preconditions on which the tool call depends still hold (e.g., the file has not been modified externally, the API endpoint is still reachable, the authorization token has not expired). This check makes TOCTOU risk explicit — the agent's decision may be based on already-changed state, and the pre-execution poll turns state drift into an observable blocking event.

(3) **Authorization check by an independent guard model**: an independent guard model whose context is isolated from the planning agent judges whether the tool call is within the current task's authorized scope. This is the only one of the three checks that involves model judgment, but the context isolation between the guard model and the planning agent makes its judgment immune to the planning agent's prompt engineering — this is the concrete instantiation of the "oversight must not depend on the overseen party's self-report" principle at the abstention exit.

The three-check design has two key constraints: ① the constraint check and the grounding check **do not rely on any model judgment** — they are performed by the watchdog's deterministic code, fully isomorphic to "the watchdog must be a deterministic rule that does not depend on any AI judgment" above; ② the guard model's context must be **physically isolated** from the planning agent — if the guard model reads the planning agent's context, the planning agent's prompt engineering can contaminate the guard model's judgment, reducing the authorization check to a declarative prohibition.

⚠️ Evidence grade B (verifiable preprint, arXiv:2606.02965v2). Three limitations: ① "the Checkpoint three-check converges 7 models' SR to 87.5–91% with significant UR recovery" comes from a **preliminary evaluation of 144 scenarios** and **must not be extrapolated to production expectations** — the absolute values depend on the test-task distribution and model combination; ② the paper's Checkpoint is constructed for its paired safety-control-group evaluation, and its form has a domain gap from production tool-call boundaries — this framework cites only the **structure** of the three checks (constraint / grounding / authorization), not its specific interdiction rates; ③ the context isolation between the guard model and the planning agent is an experimental setup in the paper; the engineering cost of isolation in production (independent model instance / independent context window / independent deployment domain) is not empirically measured — deployers must assess the trade-off between isolation cost and abstention benefit themselves.

**Relationship to existing provisions**: this section does not add a new class of watchdog rules — it upgrades the abstention exit (one of the three signals in spec/04) from "the agent declares abstention on its own" to "the watchdog enforces abstention at the tool-call boundary". This is directionally consistent with the conclusion of "declarative prohibitions do not bind" — the abstention exit cannot rely solely on "if uncertain, abstain" written in the prompt; it must have a runtime enforcement layer as backstop. On the code side this falls under G6 (notary), which is not closed; this section registers the requirement without implementation. Until G6 closes, the constraint check and the grounding check (both deterministic code) can be carried by existing watchdog rules; the guard-model authorization check is not yet mandatory.

## The No. 3 notary: an existing real-world model
No. 3 runs in an independent hardware trust domain, maintains the hash chain, performs double-blind assessment, and verifies reports against real-world results (not reports against reports). Empirical corroboration: METR and Redwood Research issued investigation reports as independent third parties, and OpenAI publicly confirmed the accuracy of their numbers — this is the real-world form of the No. 3 notary; it does not need to be invented from scratch, only institutionalized.
No. 3 must be split into two independent entities. The reason is "when the examiner also externalizes evidence, independence fails at the mechanism level". The split is as follows:
No. 3-A (examiner / honeypot-injection party): responsible for constructing known-violation samples, injecting honeypots, and generating double-blind assessment problems. It never touches the evidence chain and does not know which samples will be re-checked.
No. 3-B (evidence externalization / hash-chain maintenance party): deployed independently of No. 3-A; it only writes observed execution evidence into the Merkle hash chain and issues proofs. It does not participate in problem-setting and cannot foresee the assessment samples.
Source of independence: the two belong to different trust domains and operational parties; if either is compromised or colludes, the other can still provide the unpolluted half. This is isomorphic to "witnesses of each other" — not backups of each other, but witnesses of each other.

**What No. 3-B maintains is not a log, but a persistent record joining three things: the governance decision, its context, and its configuration.** A model close to this framework's own setting is the governance-aware multi-tenant AI sandbox: *AI Sandbox: Technical Report* (Muhammad Waseem et al., 11 authors including Pekka Abrahamsson; arXiv:2608.02679, 2026-08-02) proposes a reference architecture that **separates the multi-tenant UI from the backend control plane** and places execution and data management in mutually independent layers; the platform supports controlled user onboarding, project-centric collaboration, managed AI-service access, approval workflows, audit logs, and reproducible experiments, and explicitly stores **experiment configuration, contextual information, and governance decisions themselves as persistent records**.

This deserves emphasis: only when all three are present can one afterwards answer "under which rules, in what state, was this verdict reached". An action log alone cannot answer that question — which is precisely why "yesterday's logs against today's rules" fails silently, and why the evidence-integrity chapter requires rule changes to produce two levels of digest.

⚠️ Grade B. Limitations: ① this is a **technical report** describing the authors' own system, with **no controlled experiment and no third-party evaluation** — it is **architectural feasibility evidence**, not evidence of effectiveness; ② its being "governance-aware" is the system's own stated design goal, with no measured behavior under adversarial conditions.

**No. 3-B's capability boundary: it guarantees "not tampered with", not "content is correct".** This must stay consistent with "logging is not attribution", and there is a deployed engineering model to compare against. *GEN-RWD Sandbox* (Benedetta Gottardelli, Roberto Gatta, Leonardo Nucciarelli, Andrada Mihaela Tudor, Erica Tavazzi, Mauro Vallati, Stefania Orini, Nicoletta Di Giorgi, Andrea Damiani — 9 authors; *BMC Medical Informatics and Decision Making* 24(1):170, 2024-06-17, DOI 10.1186/s12911-024-02549-5) is a modular multi-agent platform for distributed analytics in healthcare, whose goal is to let external researchers use hospital data **without any need for direct data sharing**; the platform incorporates an **IAM agent** and a **blockchain-based notarisation module**, and the authors state that the certification agent exists to "establish a mechanism for notarising the analyses conducted and certifying both the authenticity of the content received and its successful fruition by the user", thereby providing **immutable guarantees for both parties** on the analyses carried out.

That statement yields two properties No. 3-B must have: ① **notarization is bilateral** — it notarizes both "what was produced" and "that the receiving party did receive and use it", so each side obtains its own immutable guarantee; ② **the notarization module must be independently reusable** — the paper states explicitly that "the Blockchain and Certification agent constitutes a notarisation and digital signature agent that can also be used to certify the communication exchanges in other settings".

More noteworthy is the paper's **self-declared boundary**, which corroborates this framework's restraint from the outside: aspects relating to data management and the trustworthiness of results are **left entirely to the platform's manager** — the sandbox is **in fact agnostic with respect to the data and tasks provided**; consequently preprocessing, data cleaning, and the identification and management of possible biases in the provided information, all of which are frequent problems in real data analysis, **are not handled automatically by the platform but remain the responsibility of the algorithm and data provider**. In other words, a real, deployed system equipped with a blockchain notarization module **also does not extend notarization to correctness of content**.

⚠️ Grade B. Limitations: ① the platform targets **distributed analytics for healthcare research**, not an Agent execution stack — this is a cross-domain citation, and this framework cites only the **design shape and self-declared boundary of its notarization mechanism**, not its performance or any healthcare-specific conclusion; ② the "immutable guarantees" above are the paper's **stated design goal**, and the paper provides no measured evidence of that guarantee under adversarial conditions; ③ it must **not** be phrased as "blockchain notarization guarantees that analysis results are trustworthy".

**Since notarization does not cover content correctness, that boundary should itself become a field in the protocol rather than a disclaimer on paper.** *AIREP: A Protocol for Per-Decision Evidence in AI Runtime Governance* (arXiv:2608.21363, 2026-08) provides exactly that form: each governance decision is recorded as a single signed object (a closed verb set: release / block / defer / redact / escalate_to_human / kill), inputs, outputs, and evidence are **referenced by hash rather than embedded by value**, and the record **explicitly declares what the evidence covers and what it does not cover** (scope.covers / scope.does_not_cover); records form a SHA-256 hash chain with previous included in the preimage, so any party can verify offline; a dual-language (Python / Node) conformance suite is also provided.

Of these, **scope.does_not_cover is one clause this framework did not previously have**, and it precisely upgrades GEN-RWD's self-declared boundary above from "a sentence of prose" to "a machine-checkable field": **a notarized object must carry a declaration of its own scope of non-applicability**, otherwise "notarized" will inevitably be read as "verified". This framework accordingly adds one requirement on No. 3-B — **a notarization record must include an explicit does_not_cover declaration; its absence is itself treated as incomplete notarization**.

⚠️ Grade C. Three limitations: ① **conflict of interest** — the paper is signed Phionyx Research / founder@phionyx.ai and states that its only producer is the author's own system, so its **self-description as "vendor-neutral" must not be cited**; ② its "mechanical neutrality test" verifies only **formal neutrality** (the core schema still passes after profiles are removed), **not substantive neutrality**; ③ this framework **adopts only the scope.does_not_cover field design as a candidate**, not the rest of the protocol, and does not designate AIREP as its notarization implementation.

## Double-blind assessment (the only scientific way to measure the overseer)
Use known-violation samples (honeypot injection) to measure No. 2's recall and false-positive rates, preventing both No. 2 coasting and No. 2 turning into a harsh official farming KPIs.
## Logic-invisible / sealed-memorial-style reporting
No. 2's reporting path is invisible to No. 1, preventing No. 1 from evading oversight logic. This is the multi-agent version of the Ming dynasty's sealed-memorial system.

## Minimal runnable reference implementation
The watchdog and No. 2 detection ideas in this chapter already have a runnable engineering exemplar: `reference/runtimes/l2-runtime-oversight/` (runs directly on Node 22+; `demo.ts` contains 16 groups / 72 assertions, including 9 adversarial groups). It turns "the watchdog must be deterministic hard rules" into code: lease/heartbeat stop-on-loss, first event must be lifecycle, ownerId injected by the runtime and unfakeable at the tool layer, critical-write failures refuse partial success, capability gating fails loud. **Limitation**: this implementation is a design sketch, not a compliant implementation — lease authority is an in-memory placeholder, the audit hash is a placeholder (equal-length tampering can evade detection, self-exposed in demo [12d]), there is no E1 kernel-side collection or E5 independent trust-domain sealing, no resource ledger, and no No. 3 notary; before the P3 stage (independent hardware domain + remote attestation) lands, it must not be used as a trust root on its own. The itemized honesty boundaries are in that directory's README.
