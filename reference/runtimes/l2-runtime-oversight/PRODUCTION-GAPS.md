# 生产级差距清单（PRODUCTION-GAPS）

> 本文件是 l2-runtime-oversight 参照实现的**一级章节性文件**，把生产级缺口集中到一处，逐项给出：**现状 → spec 锚点 → 差距描述 → 最小缓解路径**。
>
> 目的：避免读者把这份参照实现误读为"可上生产的监察器"。它是一份**可运行的设计草图**——把"确定性硬闸门应该怎么写"变成可读、可复现的代码，但每一项生产级能力都尚未落地。
>
> **v2.2.0 更新**：G1（租约权威存储）与 G2（审计哈希强度）已在本实现内部最小化闭合——`SqliteLeaseAuthority`（Node 22+ 内置 `node:sqlite`，零外部依赖）与 SHA-256 哈希链（Node 内置 `node:crypto`）。闭合指的是：**演示级持久化与密码学强度已达成**；生产级仍需 PostgreSQL / 独立信任域（G1）与独立信任域签名比对（G2 的 E5 部分）。**其余 6 项（G3–G8）未闭合**，见下表。
>
> **v2.5.0 更新**：G9（配置内容审查）已在本实现内部最小化闭合——`ConfigReviewer` 把 `spec/02-architecture.md` 第四条「配置权即攻击面」的五项检查点（明文凭据内联 / 共享范围扩大 / 审批步骤关闭 / 网关公开化 / 脱敏弱化）落成确定性规则，并经 `EntryGuard` 注入接入入口检查管道；demo `[19]` 组 15 项断言全绿。闭合指的是：**演示级的配置内容审查能力已达成**——每项检查都是确定性字符串/结构匹配，不依赖 AI 判断；生产级仍需语义级配置 schema 与意图分析（见下表 G9）。

## 为什么单独成章

v2.1.0 之前，这 8 项缺口分散在三处：`index.ts` 顶部注释一段、demo 的自曝用例（`[12d]` 占位哈希碰撞、`[14a]` 错误洪泛）两处、README 的"诚实边界"表格一处。读者很容易只看到其中一处就形成判断。把它们汇成一个一级章节并编号 G1–G8，是为了让任何引用本实现的人在同一个地方看到完整的边界声明——这也符合本框架 spec/13「诚实传统」的纪律：**边界要显式、要集中、要可引用**。v2.5.0 新增 G9（配置内容审查）沿用同一编排：先在 spec/02 写下概念，再在本文件登记为独立条目，并在 demo `[19]` 组给出可运行验证。

## 逐项详解

### G1. 租约权威存储 ✅ 演示级闭合（v2.2.0）

- **原缺口**：`InMemoryLeaseAuthority`（`index.ts` §1）把所有租约状态放在进程内存 `Map` 中。进程崩溃即全部丢失，重启后无法恢复租约归属。
- **闭合内容**：v2.2.0 新增 `SqliteLeaseAuthority`（`index.ts` §1b），接口与 `LeaseAuthority` 完全一致：
  - 租约状态落盘（SQLite 文件）；demo `[18c]` 验证"写盘 → close 模拟崩溃 → 重开同一文件 → 租约状态仍在、心跳语义不变"；
  - 使用 Node 22+ 内置 `node:sqlite`，零外部依赖；
  - `InMemoryLeaseAuthority` 保留，供纯内存场景（无文件系统）使用。
- **剩余差距（生产级）**：SQLite 是单文件单进程锁——被观测进程若与租约权威同机同权限，仍可通过文件篡改伪造租约。spec/09 要求权威在**独立信任域**：生产应换 PostgreSQL（独立进程）或独立信任域存储。接口形态不变，替换后端不需要改任何监察逻辑。
- **关联代码**：`index.ts` §1b（`SqliteLeaseAuthority`）；demo `[18]` 组。

### G2. 审计哈希强度 ✅ 演示级闭合（v2.2.0）

- **原缺口**：占位哈希 `h{seq}:{prevHash前6位}:{payload长度}` 不提供密码学抗篡改保证；等长替换可漏检（原 demo `[12d]` 自曝）。
- **闭合内容**：v2.2.0 起 `AppendOnlyAuditLog` 的哈希为真实 **SHA-256**（`index.ts` 导出 `sha256()`，Node 内置 `node:crypto`，零外部依赖）：
  - 每条事件哈希绑定 `{seq, type, data, ts, prev}` 全量载荷与前一哈希；
  - demo `[12d]` 从"自曝等长碰撞漏检"改为**验证闭合语义**："SHA-256 下等长篡改必被检出（verifyChain()===false）"；
  - demo `[12e]` 验证哈希形态为 64 位 hex。
- **剩余差距（生产级）**：E5 要求的"独立信任域签名比对"仍未实现（见 G4）——哈希链在被观测进程内计算，进程被攻陷时哈希链本身可被整体重算。SHA-256 闭合的是**等长篡改漏检**这一具体缺口，不是完整的 E5。
- **关联代码**：`index.ts` §5（`AppendOnlyAuditLog` / `sha256`）；demo `[12]` 组。

### G3. E1 内核侧采集

- **现状**：所有审计事件（`AuditEvent`）产生于被观测进程内部，经用户态路径（`emit` 函数）写入审计链。
- **spec 锚点**：`spec/02-architecture.md` E1："证据采集应在内核侧（eBPF / LSM 等）进行，不经用户态路径——被观测方即使攻陷了用户态也无法伪造或删除证据。"
- **差距描述**：进程内采集无法对抗用户态被攻陷的场景——一个攻陷了被观测进程的对抗者可以篡改 `emit` 函数本身。
- **最小缓解路径**：本实现无法独立解决——需要内核态组件（如 AgentSight / mcpguard-dynamic 的 eBPF 探针）。本实现的角色是**定义审计事件的语义与链结构**，内核侧采集组件对接这一语义即可。
- **关联代码**：`index.ts` L277–L319（`AppendOnlyAuditLog`）；`RuntimeOverseer.run` 中的 `emit` 闭包（L387–L395）。

### G4. E5 采集点完整性

- **现状**：审计链存储在被观测进程的同一地址空间内，无独立信任域、无采集模块签名。
- **spec 锚点**：`spec/02-architecture.md` E5："采集模块自身须在独立信任域运行、须有签名、须能被远程证明。"
- **差距描述**：无独立信任域意味着采集模块本身可以被攻陷；无签名意味着无法证明采集到的证据未被篡改。
- **最小缓解路径**：本实现无法独立解决——需要独立硬件信任域（如 TPM / SEV-SNP / Intel TDX）与远程证明协议。本实现的角色是**定义证据链的语义**，独立信任域固化组件对接这一语义即可。
- **关联代码**：`index.ts` L277–L319（`AppendOnlyAuditLog`）。

### G5. 资源账本

- **现状**：`RuntimeOverseer` 只跟踪 `attempt` 与 `lease TTL`，不跟踪资源消耗（预算比、影子比、记忆写入次数）。
- **spec 锚点**：`spec/10-resource-ledger.md`："资源账本记录每次工具调用的资源消耗（token / 内存 / 磁盘 / 网络）、每次记忆写入的字段差异、影子比（实际消耗 / 预算）。"
- **差距描述**：无资源账本意味着无法检测"预算耗尽仍继续执行"、"影子比超阈值"、"记忆写入未审计"等违规。
- **最小缓解路径**：扩展 `RunContext`，注入一个 `ResourceLedger` 接口（记录预算、消耗、影子比），让 `execute` 回调在每次工具调用前后报告资源变化。接口形态可参考本实现的 `LeaseAuthority`——定义在 `index.ts`、占位实现先放 demo 中。
- **关联代码**：`index.ts` L371–L435（`RuntimeOverseer`）；L437–L441（`RunContext`）。

### G6. 三号公证机

- **现状**：无独立公证服务、无三号甲 / 乙拆分、无 Merkle 双盲。
- **spec 锚点**：`spec/09-oversight.md`："三号公证机是独立硬件信任域，三号甲与三号乙拆分运行，通过 Merkle 双盲交叉验证，互为证人但不互通信。"
- **差距描述**：无独立公证意味着本实现**不能单独用作信任根**——在被对抗性多 Agent 场景（P3 阶段）下，本实现产出的证据链可以被被观测方篡改而不被交叉发现。
- **最小缓解路径**：本实现无法独立解决——需要独立的公证服务（独立进程 + 独立信任域 + Merkle 双盲协议）。本实现的角色是**产出可被公证的审计事件流**，公证服务订阅这一事件流即可。
- **关联代码**：`index.ts` L277–L319（`AppendOnlyAuditLog`）。

### G7. 信用分与信用回避

- **现状**：无信用分演化、无信用回避阈值。
- **spec 锚点**：`spec/04-credit-abstention.md`："信用分随历史行为演化，低于阈值的 Agent 须被信用回避（不允许接管高风险任务）。"
- **差距描述**：无信用分意味着本实现无法基于 Agent 的历史行为做准入决策——任何通过租约抢占的 Agent 都被视为同等可信。
- **最小缓解路径**：本实现无法独立解决——需要与 L1 内生对齐层的信用分子系统对接。本实现的角色是**提供可作为信用分输入的事件流**（成功 / 失败 / 超时 / 违规），信用分子系统消费这一事件流即可。
- **关联代码**：`index.ts` L371–L435（`RuntimeOverseer`）中的 `session_end` 事件。

### G8. 群治理与涌现检测

- **现状**：`RuntimeOverseer` 是集中调度模型（一个 runner 管一个 session），无交互图谱、无涌现信号检测、无规模熔断。
- **spec 锚点**：`spec/07-swarm-governance.md`："监察对象从行为日志升级到交互图谱；七类涌现信号（消息速率突变、拓扑收敛、角色固化、自发指挥、协同攻击、信息囤积、规模超阈）须被持续检测。"
- **差距描述**：集中调度模型无法看到 Agent 之间的交互——即使每个 Agent 的行为都合规，它们可能在交互层面涌现出系统级风险。
- **最小缓解路径**：本实现无法独立解决——需要从集中调度模型扩展到分布式交互图谱。本实现的角色是**为每个 Agent 提供行为级证据**，交互图谱层在行为级证据之上构建。
- **关联代码**：`index.ts` L371–L435（`RuntimeOverseer`）。
- **特别说明**：这是全体系最大的工程缺口，也是 `spec/13-boundaries.md` 的开放问题 #15——**对去中心化蜂群（狼群），目前只有检测能力，尚无经实证可靠的反制手段**。本实现对这一缺口无能为力，如实声明。

### G9. 配置内容审查（配置权即攻击面）✅ 演示级闭合（v2.5.0）

- **原缺口**：变更准入只考核「变更是否让系统变差」（能力增益 / 回归量），不考核「变更是否把不安全参数写进了已授权的工作流」。spec/02 第四条明确：**性能不回归不等于安全不退化**——关掉一个审批步骤会提升通过率、不触发任何回归告警，两道准入判据都会放行，但工作流已经变成攻击面。
- **spec 锚点**：`spec/02-architecture.md` L98–L100（第四条——配置权即攻击面）。证据等级 B（可核查预印本）：HarnessRisk（arXiv:2608.17597）在三个 harness 六阶段生命周期评测显示**配置阶段是最脆弱的阶段**；引用其定性结论与成因分析，不引用攻击成功率区间作为生产预期。
- **闭合内容**：v2.5.0 新增 `ConfigReviewer`（`index.ts`），并把 spec/02 L100 明列的五项审查落成确定性规则：
  - ① 凭据明文内联（inline-credential）——字符串/结构匹配，容忍 JSON 键引号与裸键名两种形态；
  - ② 共享范围扩大（share-scope-widened）——visibility/share/shareWith/accessLevel 设为 public / 通配 / org-wide 等；
  - ③ 审批步骤关闭（approval-disabled）——requireApproval/approvalRequired/reviewRequired 设为 false/off 等；
  - ④ 对外网关公开化（gateway-publicized）——gateway/endpoint/host 从内网（127.0.0.1/10.x/192.168.x）改为 0.0.0.0/公网域名/通配；
  - ⑤ 脱敏强度弱化（redaction-weakened）——redact/redaction/pii/mask 设为 off/none/disabled 等。
  - 接入方式：`EntryGuard` 新增可选构造参数 `configReviewer` + `configTools`——被标记为「配置变更类」的工具调用，在参数策略之外、执行之前追加这道审查（`EntryDenyCategory` 相应新增 `config-review-fail`）；不注入则不启用（向后兼容）。审查目标自动适配：args 形如 `{ config: {...} }` 时审查 `args.config` 子字段，否则审查整体 args。
  - demo `[19]` 组 15 项断言全绿：五项各自拦截、复合恶意配置一次命中多项、良性变更放行（不误伤正常运维）、内网网关不误报、拦截留痕（审计事件 × 6）、端到端（`guardedToolCall` 管道中恶意配置变更被拦在入口、execute 零调用）、`ConfigReviewer` 可独立用于变更准入流水线。
- **剩余差距（生产级）**：每项检查都是**确定性的字符串/结构匹配**——演示语义，不覆盖所有攻击变体。生产级审查需要：(a) 语义级配置 schema（而非字段名枚举——命名混淆如 `reqApprov` 可绕过字段名匹配）；(b) 意图分析（间接引用：凭据不内联而是指向外部引用也可能泄露）；(c) fail-closed 语义（当前检查规则自身抛错时视为未命中，生产实现应考虑结构不匹配即拦）。本实现的检查规则集可通过构造参数注入自定义检查集（`ConfigReviewer.DEFAULT_CHECKS` 可替换）。
- **关联代码**：`index.ts`（`ConfigReviewer` / `EntryGuard` 规则 3）；demo `[19]` 组。

## 总结性声明

本实现**仍不能单独用作信任根**。在 `spec/02` 所述 P3 阶段（独立硬件域 + 远程证明）落地之前，它只是把"确定性硬闸门应该怎么写"变成可运行、可复现的参照。上述 9 项缺口中：

- **G1、G2 已在演示级闭合**（v2.2.0：SQLite 持久化租约 + SHA-256 哈希链）——闭合的是"崩溃恢复"与"等长篡改漏检"两个具体缺口；生产级仍需 PostgreSQL / 独立信任域与 E5 签名比对；
- **G9 已在演示级闭合**（v2.5.0：`ConfigReviewer` 五项配置内容审查 + `EntryGuard` 接入）——闭合的是"配置变更的工具调用在执行前多一道内容审查"这一具体缺口；生产级仍需语义级配置 schema 与意图分析；
- **G5** 可在本实现内部扩展接口（加 `ResourceLedger`）；
- **G3、G4、G6、G7、G8** 需要外部系统配合（内核态组件、独立信任域、公证服务、信用分子系统、交互图谱层），超出本实现的代码范围。

引用本实现时，**必须同时引用本文件**——这是本框架"诚实边界"纪律的直接落地。
